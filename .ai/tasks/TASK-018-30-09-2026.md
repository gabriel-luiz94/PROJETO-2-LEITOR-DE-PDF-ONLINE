# TASK-018-30-09-2026

## Objetivo

Regras de domínio **próprias de cada projeto**: criar uma regra que existe só num projeto, alterar ou desligar uma regra
do padrão só num projeto, e ver de onde vem cada regra — sem copiar a lista inteira e sem perder as atualizações do padrão.

## Contexto

Camada 2 do ADR-004. Pedido do usuário (2026-09-30): "poder criar regras únicas por projeto". Independe da TASK-016 na
parte de armazenamento/herança; a UI dessa herança usa o editor da TASK-017. Projetos hoje: PARAIBA (`027`) e RONDONIA
(`229`), mais os que o admin cadastrar.

## Situação atual

- `routers/validacao_regras.py:buscar_regras`: devolve a versão do projeto **se existir**, senão a `DEFAULT`. A versão de
  um projeto é uma **cópia integral** da lista (`regras_dominio.regras_json` = array).
- Consequências: (a) para ter **uma** regra só do projeto é preciso salvar a lista inteira; (b) depois disso o projeto
  **para de receber** qualquer mudança/regra nova do padrão (por isso existe o botão "Adicionar regras novas da
  semente", que é um remendo); (c) não há como ver o que difere do padrão; (d) o mesmo se aplica a ajustar só a
  severidade ou desligar uma única regra num projeto.
- Prompts de validação (TASK-012) já são por projeto com fallback; não fazem parte desta task.

## Comportamento desejado

**Modelo em camadas (herança):** o efetivo de um projeto = padrão (`DEFAULT`) + ajustes do projeto.

1. **Regra exclusiva do projeto:** "Adicionar regra só neste projeto" — existe apenas no efetivo desse projeto.
2. **Ajuste de regra herdada:** neste projeto, mudar `ativa`, `severidade`, `mensagem`, `operacoes` ou parâmetros de uma
   regra do padrão, **sem tocar** no padrão nem em outros projetos ("sobrescrita").
3. **Desligar/ocultar uma regra do padrão** só neste projeto.
4. **Origem visível:** cada regra mostra um selo — *padrão*, *sobrescrita neste projeto* ou *só deste projeto* — e
   "voltar ao padrão" desfaz a sobrescrita de uma regra.
5. **Padrão evolui, projeto acompanha:** regra nova ou correção no padrão aparece nos projetos (respeitando as
   sobrescritas); o botão "Adicionar regras novas da semente" deixa de ser necessário para projetos.
6. **Armazenamento:** o registro do projeto guarda só o **overlay** (`adicionadas`, `sobrescritas`, `removidas`), no
   mesmo `regras_json` (TEXT) — **sem SQL novo no Supabase**. Leitura aceita os dois formatos (array antigo = cópia
   integral; objeto = overlay), com migração automática e idempotente no primeiro salvamento (ou em lote pelo admin).
7. **Histórico e reversão** continuam por projeto; a validação de schema roda sobre o efetivo antes de salvar.
8. `POST /api/validacao/planilhas` e o painel de teste usam o **efetivo** do projeto.

## Restrições

- Migração **não pode mudar o resultado** das validações de projetos que já têm versão salva: a cópia integral antiga
  vira overlay equivalente (diferenças em relação ao padrão) e o efetivo é idêntico (teste com dados reais do banco).
- Não apagar tabelas nem dados; padrão de evolução do `database.py` (idempotente).
- Rotas de escrita só admin; leitura para autenticados.
- Contratos (Regra 5): [x] Schema do Supabase — **formato do JSON muda, tabela não**. Documentar no ADR-005.

## Critérios de aceite

- [ ] Criar uma regra só do projeto `229` sem copiar a lista; o `027` e o `DEFAULT` não a enxergam
- [ ] Sobrescrever a severidade/desligar uma regra herdada só no `229`; o padrão e o `027` ficam intactos
- [ ] Alterar o padrão (regra nova / correção) chega ao `229` e ao `027`, exceto onde há sobrescrita
- [ ] "Voltar ao padrão" desfaz a sobrescrita de uma regra
- [ ] Selos de origem corretos na tela; efetivo idêntico ao de antes para projetos já com versão salva (migração)
- [ ] Histórico/reversão por projeto funcionam com o overlay; sincroniza com o Supabase sem SQL novo
- [ ] Testes (incluindo migração e equivalência) e verificação no navegador; `.ai` e STATE/CHANGELOG atualizados

## Exemplos

Padrão: `C2-CFU-SUPL` (aviso). No projeto `229`: severidade → `erro`, e regra nova `PROJ229-POSTE12` só dele.
Efetivo do `229` = padrão com `C2-CFU-SUPL` em erro + `PROJ229-POSTE12`. Efetivo do `027` = padrão puro.

Overlay armazenado (esboço): `{"versao": 2, "sobrescritas": {"C2-CFU-SUPL": {"severidade": "erro"}}, "adicionadas": [{...}], "removidas": []}`

## Arquivos potencialmente afetados

- `routers/validacao_regras.py` — `regras_efetivas`, salvar overlay, migração, origem por regra; `adicionar-novas` obsoleto
- `services/regras_dominio.py` — função pura de mesclagem (padrão + overlay) e de cálculo do overlay (diff)
- `database.py` — migração idempotente das versões de projeto existentes (sem apagar dados)
- `static/admin.js`/`admin.html` — selos, "adicionar só neste projeto", "voltar ao padrão"
- `tests/test_regras_dominio.py`, `.ai/decisions/ADR-005-*.md`, `.ai/VALIDACOES.md`, `.ai/CONTEXT.md`

## Riscos

- **Migração alterar resultados** de projetos existentes: teste de equivalência efetivo-antes = efetivo-depois.
- Dois admins editando o mesmo projeto ao mesmo tempo (último a salvar vence): documentar; não tratar agora.
- Conflito ao remover no padrão uma regra que um projeto sobrescreveu: definir e testar (sugestão: a sobrescrita órfã é
  ignorada e listada como aviso para o admin).

## Plano de teste

pytest: mesclagem (adicionar/sobrescrever/remover/voltar ao padrão), migração array→overlay com equivalência, isolamento
entre projetos, histórico/reversão do overlay, rotas com permissões. Navegador: fluxo dos selos e ações. Declarar o que
não foi possível verificar (sincronização real com o Supabase).

## Decisões a confirmar com o usuário

1. O modelo em **camadas** (herança + ajustes) é o desejado, ou você prefere projetos totalmente independentes
   (cada um com sua lista completa, como hoje, só com uma UI melhor)? (recomendação: camadas.)
2. Quando o padrão muda uma regra que um projeto **já sobrescreveu**, vale a do projeto? (sugestão: sim.)
3. Um projeto pode **excluir** (ocultar) uma regra do padrão, ou apenas desligá-la? (sugestão: só desligar, para manter
   visível que a regra existe.)
4. Quem cria regra exclusiva de projeto: só admin (como hoje) ou também um "admin de projeto"? (hoje só há admin/operador.)
