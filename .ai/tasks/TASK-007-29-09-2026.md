# TASK-007-29-09-2026

## Objetivo

Tornar a Tabela de Processamento e a Tabela de Classificação do leitor (TASK-006) editáveis pelo
modal "Regras do Leitor", restrito a usuários com role `admin`.

## Contexto

A TASK-006 já criou as duas tabelas de regras, o motor (`static/regras_leitor_engine.js`) e os
endpoints CRUD completos (`GET`/`POST /api/regras-leitor/processamento` e `/classificacao` —
`routers/regras_leitor.py`). O `POST` já substitui a lista inteira de regras de um projeto. O app
já tem controle de role (`middleware/auth_middleware.py:require_role`, JWT carrega `role`, default
`"operador"`), usado hoje em `/admin`.

## Situação atual

- `abrirModalRegrasLeitor()` (`static/script.js`) só lista as regras — modo leitura.
- Os endpoints `POST` já existem e funcionam, mas **hoje não têm nenhuma restrição de role** —
  qualquer usuário autenticado poderia chamá-los diretamente (fora da UI) e sobrescrever as regras
  de um projeto.
- Não existe validação de schema no `POST`, nem histórico de versões — o payload novo simplesmente
  sobrescreve o antigo.

## Comportamento desejado

Usuários com role `admin` veem, dentro do modal "Regras do Leitor", controles completos de edição
para as duas tabelas (Processamento e Classificação). Usuários sem essa role continuam só
visualizando, como hoje.

**Decisões de refinamento (2026-09-29, todas confirmadas pelo usuário):**

1. **Edição via formulário estruturado por regra** — não editor de JSON bruto. Cada regra abre um
   formulário com os campos certos para o seu modo (`DEFINIR`/`SUBSTITUIR`/`SUBSTITUIR_TOTAL`) e
   fase (1/2/3 no Processamento), incluindo `vizinhanca` quando aplicável. Mesma lógica para a
   Tabela de Classificação (`operacao_em`, `ativo_regex`, `cor`/`layer_em`, `texto_regex`, etc.).
2. **Validação de schema no backend antes de salvar**: campos obrigatórios por modo/fase
   preenchidos, e toda regex informada precisa compilar (`re.compile` no backend) — se algo for
   inválido, o `POST` rejeita com erro claro (400) em vez de salvar. Mantém a garantia de que o
   motor de regras nunca recebe um payload que o quebre.
3. **Reordenação por drag-and-drop**: a ordem das regras dentro de cada fase (Processamento) ou da
   lista (Classificação) já É a ordem de execução do motor (não existe campo `ordem` separado) —
   arrastar uma regra na lista reordena o array que é salvo, sem precisar de um campo extra.
4. **Rotas `POST` protegidas por `Depends(require_role("admin"))`** — a proteção passa a existir
   tanto na UI (só admin vê os controles) quanto no backend (só admin consegue de fato salvar,
   mesmo chamando a API direto). O `GET` continua aberto (é só leitura, usado pelo motor em tempo
   de leitura para todo usuário).
5. **Histórico de versões com reversão**: cada vez que um admin salva, a versão anterior é
   preservada (não sobrescrita/perdida). O admin consegue ver as versões anteriores e reverter para
   uma delas. Reverter é tratado como um novo salvamento (a versão "atual" no momento da reversão
   também vira uma entrada de histórico, nunca é descartada).
6. **"Testar regra" antes de salvar**: o formulário de edição tem uma seção para informar um
   texto/cor/layer de exemplo (e operação/ativo, no caso da Classificação) e ver o resultado
   rodando `RegrasLeitorEngine` **no navegador**, sem precisar salvar nem rodar uma leitura real.

   **Decisão de implementação (não perguntada explicitamente, registrada aqui por transparência):**
   o teste roda o **conjunto de regras em edição** (Processamento + Classificação, incluindo
   mudanças ainda não salvas), não só a regra isolada sendo editada — isso é o que realmente
   importa, já que o resultado de uma regra depende da ordem e das regras vizinhas (`parar`,
   fases). Se o usuário preferir testar só a regra isolada (mais simples, mas não pega bug de
   interação/ordem), avisar antes de implementar.

## Restrições

- Não altera o motor de regras (`regras_leitor_engine.js`) nem a forma como ele interpreta as
  regras — só a capacidade de criá-las/editá-las pela UI em vez de só pelo banco.
- Não muda o contrato dos endpoints já existentes usados pelo motor em tempo de leitura (formato
  do payload `{projeto_codigo, regras}` no `GET`).

Contratos do `RULES.md` (Regra 5) que esta tarefa toca:
- [x] Schema do Supabase — **muda**: novas tabelas de histórico (ver "Arquivos potencialmente
      afetados"). As tabelas existentes (`regras_leitor_processamento`/`_classificacao`) não mudam
      de formato.

## Critérios de aceite

- [ ] Usuários com role `admin` veem controles de edição (adicionar/editar/remover/reordenar
      regra) nas duas tabelas do modal "Regras do Leitor"; usuários sem essa role continuam vendo
      só a visualização atual (read-only).
- [ ] Edição é via formulário estruturado por regra — os campos mudam conforme o modo
      (`DEFINIR`/`SUBSTITUIR`/`SUBSTITUIR_TOTAL`) e a fase da regra.
- [ ] Reordenar regras via drag-and-drop atualiza a ordem real usada pelo motor.
- [ ] O backend valida a regra antes de salvar (campos obrigatórios por modo, regex compila) e
      rejeita com mensagem clara se algo for inválido — nunca salva um payload que quebre o motor.
- [ ] Rotas `POST /api/regras-leitor/processamento` e `/classificacao` exigem role `admin`
      (retornam 403 para outros usuários); `GET` continua aberto.
- [ ] Cada salvamento preserva a versão anterior no histórico; o admin consegue visualizar
      versões anteriores e reverter para uma delas pela UI.
- [ ] O formulário de edição tem um "testar" que roda o motor no navegador com um texto/cor/layer
      de exemplo, usando o conjunto de regras em edição (mudanças ainda não salvas incluídas), e
      mostra o resultado (operação/ativo/entidade).
- [ ] Resultado da classificação de leituras existentes não muda, a menos que o admin edite
      regras de propósito (RULES.md Regra 8 — preservar comportamento salvo intenção explícita).
- [ ] Documentação `.ai` atualizada conforme `RULES.md` Regra 9.
- [ ] `STATE.md` atualizado conforme `RULES.md` Regra 10.

## Exemplos

### Entrada

Admin edita, na fase 3 de Processamento, a regra de `BLOCO`+`TERRA3` (cor vermelha), mudando o
`ativo_template`, e usa "testar" com `texto="1-BLOCO TERRA3"`, `cor=#FF0000`, `layer="01_ORCAMENTO"`
antes de salvar.

### Resultado esperado

O painel de teste mostra o `operacao`/`ativo` que essa entrada geraria com as regras **em edição**
(não as salvas), permitindo ao admin conferir antes de persistir. Ao salvar, a versão anterior da
Tabela de Processamento desse projeto fica disponível no histórico.

## Arquivos potencialmente afetados

- `static/script.js` — `abrirModalRegrasLeitor()` passa a construir um editor completo: lista
  com drag-and-drop, formulário por regra (campos condicionais por modo/fase), painel de "testar"
  (chama `RegrasLeitorEngine` diretamente no navegador, sem round-trip ao backend), controles de
  histórico/reversão. Só renderiza os controles de edição se `role === 'admin'` (o role já vem do
  JWT decodificado no login, reaproveitar o mesmo padrão de `/admin`).
- `static/index.html` — modal `#modal-regras-leitor` ganha os novos elementos de UI.
- `routers/regras_leitor.py` — `Depends(require_role("admin"))` nos `POST`; validação de schema
  antes de salvar (por modo/fase, compilar toda regex); novos endpoints de histórico (ex.:
  `GET /api/regras-leitor/{tabela}/historico?projeto_codigo=...` e
  `POST /api/regras-leitor/{tabela}/reverter` recebendo o id da versão a restaurar).
- `database.py` — novas tabelas `regras_leitor_processamento_historico` e
  `regras_leitor_classificacao_historico` (`id`, `projeto_codigo`, `regras_json`, `criado_em`,
  possivelmente `criado_por`), alimentadas a cada `POST` bem-sucedido (grava a versão **anterior**
  como uma entrada de histórico antes de sobrescrever).
- `scripts/schema_supabase.sql` — mesmas tabelas novas no Supabase.
- `middleware/auth_middleware.py` — reuso de `require_role` (já existe, não deve precisar mudar).

## Riscos

- Payload malformado não passa mais despercebido (mitigado pela validação de schema), mas a
  validação em si precisa cobrir fielmente todos os campos que `regras_leitor_engine.js` de fato
  usa — se o engine ganhar um campo/modo novo no futuro e a validação do backend não for
  atualizada junto, o admin pode ficar impedido de salvar uma regra válida (falso negativo). Mesma
  classe de risco de duplicação de lógica já registrada nas TASK-006/TASK-008 (regra decisória
  existe em mais de um lugar).
- Tabelas de histórico crescem sem limite (nenhuma política de retenção definida) — aceitável para
  o volume esperado (uma linha por salvamento, por projeto), mas vale registrar como limitação
  conhecida.

## Implementação (2026-09-29)

Implementado exatamente como planejado, com uma correção técnica descoberta ao ler
`static/regras_leitor_engine.js` com atenção antes de implementar o drag-and-drop: **o ponto 3 do
refinamento estava errado** — eu havia registrado "a ordem já é a posição do array, sem campo
`ordem` separado", mas o motor **de fato ordena por um campo `ordem` explícito** dentro de cada
fase (`regras.sort((a,b) => (a.ordem||0) - (b.ordem||0))`, em `processar()` e `classificar()`), não
pela posição no array/JSON. Corrigido antes de implementar: o drag-and-drop **reescreve o campo
`ordem`** de cada regra do grupo (múltiplos de 10, mesmo padrão de espaçamento do seed) em vez de
só reordenar o array.

**Alterado/criado:**
- `database.py` — tabelas `regras_leitor_processamento_historico`/`_classificacao_historico`
  (`id` autoincrement, `projeto_codigo`, `regras_json`, `criado_em`, `criado_por`).
- `scripts/schema_supabase.sql` — mesmas duas tabelas no Supabase (`BIGSERIAL`, índice por
  `projeto_codigo`).
- `routers/regras_leitor.py` — reescrito:
  - `validar_regras(tabela, regras)` + validadores específicos por tabela: `ordem` numérica
    obrigatória, `fase`/`modo` dentro dos valores válidos, `ativo_regex` obrigatório nos modos
    `SUBSTITUIR`/`SUBSTITUIR_TOTAL` (sem ele a regra nunca casa — o mesmo motivo que gera o "falso
    negativo" citado em "Riscos"), toda regex (`texto_regex`/`ativo_regex`/`vizinhanca.regex`)
    precisa compilar (`re.compile`), campos de lista (`cor_em`/`cor_nao_em`/`layer_em`/
    `operacao_em`) precisam ser listas. `_save_regras` chama a validação **antes** de tocar no
    banco — payload inválido nunca chega a ser persistido nem gera entrada de histórico.
  - `Depends(require_role("admin"))` nas rotas `POST /processamento`, `/classificacao`,
    `/processamento/reverter`, `/classificacao/reverter`, `GET /processamento/historico`,
    `GET /classificacao/historico`. `GET /processamento` e `/classificacao` continuam abertos a
    qualquer usuário autenticado (só leitura).
  - `_save_regras` grava a versão **atual** (antes de sobrescrever) na tabela de histórico
    correspondente, com `criado_por` = e-mail do usuário (extraído de `request.state.user`,
    populado pelo `AuthMiddleware`). Reverter (`POST .../reverter`) busca a versão pelo `id` do
    histórico e chama `_save_regras` de novo — a versão que estava vigente no momento da reversão
    também vira uma entrada de histórico (a cadeia nunca perde uma versão).
- `static/script.js` — `abrirModalRegrasLeitor()` reescrito para operar sobre um **rascunho**
  (`window.__regrasLeitorDraft`, clone profundo das regras carregadas) por tabela, reiniciado a
  cada abertura do modal. Novas funções: renderização da lista com drag-and-drop
  (`_renderRegrasLeitorTabela`, `_ativarDragDropRegrasLeitor`, `_reordenarRegraLeitor`), formulário
  estruturado por regra com campos condicionais por modo/fase (`_formHtmlRegraProcessamento`/
  `_formHtmlRegraClassificacao`, `_atualizarCamposModoRegraLeitor`), painel de teste que roda
  `RegrasLeitorEngine.processar`/`classificar` **no navegador** contra o rascunho em edição
  (`rodarTesteRegraLeitorProcessamento`/`Classificacao`), CRUD do rascunho
  (`abrirEditorRegraLeitor`/`salvarRegraLeitorDoFormulario`/`removerRegraLeitor`), persistência real
  (`salvarRegrasLeitorTabela`, `POST` para o backend, com exibição das mensagens de validação
  retornadas), histórico/reversão (`abrirHistoricoRegrasLeitor`/`reverterVersaoRegraLeitor`). Tudo
  condicionado a `localStorage.getItem('is_admin') === 'true'` (mesma checagem já usada em
  `script.js` para o botão "Admin"). Também corrigido, como efeito colateral necessário: as funções
  de descrição (`_descreverRegraProcessamento`/`_descreverRegraClassificacao`, da TASK-006) nunca
  mostravam o campo `descricao` da regra — sem isso o campo "Descrição" do novo formulário seria
  inútil (não apareceria na lista depois de salvo).
- `static/index.html` — dois novos modais: `#modal-regra-leitor-editor` (formulário) e
  `#modal-regra-leitor-historico` (lista de versões).

### Testes

RULES.md Regra 7 — sem testes automatizados no projeto, verificação manual e real:

- **Backend, via HTTP direto contra um servidor real** (venv isolada para contornar um problema
  pré-existente do ambiente com `cryptography`/`cffi` do sistema — não relacionado a este código;
  banco SQLite real, `init_db()` do zero): login como o admin seed (`admin@local.com`), confirmado
  que:
  - `GET` funciona para qualquer usuário autenticado (inclui sem role admin).
  - `POST` com regex inválida retorna `400` com a mensagem de erro específica da regra/campo.
  - `POST` válido retorna `200` e persiste.
  - Uma segunda gravação no mesmo projeto move a primeira versão para o histórico;
    `GET .../historico` lista corretamente; `POST .../reverter` restaura a versão antiga **e**
    preserva a intermediária no histórico (a cadeia cresce, nunca perde uma versão).
  - Usuário criado com role `operador`: `GET` funciona, `POST`/`GET .../historico` retornam `403`.
  - Requisição sem token retorna `401`.
- **Navegador real (Playwright, Chromium), contra o mesmo servidor real**: login real, sessão real.
  - Admin vê os botões "+ Nova regra"/"Histórico"/"Salvar alterações"; operador não vê nenhum
    (só a visualização já existente da TASK-006).
  - Criar uma regra de Processamento (`DEFINIR`) pelo formulário, testar no painel embutido
    (resultado bateu com o esperado do motor), salvar no rascunho, persistir de verdade — confirmado
    que sobrevive a um reload completo da página (não é só estado local).
  - Mesmo fluxo para Classificação (campo `entidade`), com o painel de teste mostrando a entidade
    correta.
  - Remover uma regra do rascunho reduz a lista corretamente.
  - Reordenar por drag-and-drop: confirmado que o evento `drop` realmente troca os valores de
    `ordem` das duas regras envolvidas (verificado tanto pela mudança visual quanto disparando os
    eventos `dragstart`/`dragover`/`drop` diretamente via JS, contornando uma limitação conhecida do
    `Locator.drag_to()` do Playwright em modo headless com elementos `draggable` nativos — o mesmo
    tipo de artefato de automação já registrado na TASK-006 para `select_option`; o comportamento
    real do navegador, fora da simulação do Playwright, não tem esse problema).
  - Histórico + reverter pela UI: salvar duas vezes (a segunda com uma regra extra), abrir
    "Histórico", clicar "Reverter" — confirmado que a regra extra desaparece.
  - Zero erros de página (`pageerror`) atribuíveis ao código novo — os erros de console observados
    (CDN bloqueado, certificado do proxy, WebSocket 403) já são conhecidos deste ambiente de teste e
    não têm relação com o código.
- **Validação da lógica de schema isoladamente**: as 67 regras reais do seed (45 processamento + 22
  classificação) passam pela validação nova sem nenhum falso positivo; casos quebrados propositais
  (regex inválida, `ordem` ausente, `SUBSTITUIR` sem `ativo_regex`) são rejeitados com a mensagem
  certa.
