# TASK-047-06-10-2026

**`adicionar_ativo` aceita lista de ativos fixos, todos com a mesma quantidade**

> Pedido do usuário: "CONSIGO EM UMA UNICA REGRA PASSAR PRA ADICIONAR 2 ATIVOS? [...] CONSIGO PASSAR
> UMA LISTA, TIPO 90525, 90542, 92540 EM UMA UNICA REGRA?" — depois de confirmar que a primeira
> pergunta (duas ações dentro do mesmo ajuste) já era suportada, o usuário pediu explicitamente a
> capacidade de adicionar uma LISTA de códigos fixos numa única ação `adicionar_ativo`. Confirmado
> com o usuário: "quantidade igual pra todos" antes de implementar. Implementada em 2026-10-06, logo
> após a TASK-046.

## Objetivo

Permitir que `adicionar_ativo.ativo` seja uma LISTA de códigos fixos (em vez de só um código ou do
ativo dinâmico da TASK-046) — um token novo por código da lista, todos com a MESMA quantidade `qtd`
(fixa ou dinâmica via `{"soma": ...}` da TASK-045, resolvida uma única vez).

## Contexto

Já era possível adicionar vários ativos dentro do MESMO ajuste usando várias ações `adicionar_ativo`
no array `acoes` (capacidade pré-existente, sem mudança de código — cada receita de ajuste já tinha
`acoes: [...]` desde a TASK-023). O usuário queria algo mais compacto: uma única ação com vários
códigos, sem repetir `adicionar_ativo` várias vezes só pra trocar o código.

## Situação atual (antes desta tarefa)

- `adicionar_ativo.ativo` aceitava só uma string (código fixo) ou, desde a TASK-046, um dict de
  ativo dinâmico (`{"igual_a": SELETOR, ...}`).
- Pra adicionar vários códigos fixos na mesma linha, era preciso uma ação por código.

## Comportamento desejado

1. `ativo` passa a aceitar também uma LISTA de strings (códigos fixos, sem espaço cada um) — um
   token novo por código, cada um com a MESMA quantidade `qtd`.
2. `qtd` funciona igual ao caso de um único ativo fixo: número fixo (padrão 1, negativo gera o
   prefixo `"*"`) ou `{"soma": SELETOR, "fator"?: número}` (TASK-045) — resolvida **uma única vez**
   antes de qualquer token ser adicionado, e aplicada igualmente a todos os códigos da lista
   ("quantidade igual pra todos", decisão do usuário).
3. `se_ja_existe` (ignorar/somar/substituir) funciona por código, independentemente — se um dos
   códigos já existe na linha e outro não, cada um segue a própria regra.
4. `descrever_acao()` descreve a lista em português.
5. UI (`painel_ajustes.js`): seletor "ativo" ganha uma terceira opção "lista de códigos" (além de
   "fixo" e "igual ao ativo encontrado" da TASK-046) — campo de texto com códigos separados por
   vírgula, mesmo padrão já usado em outros campos de lista da gaveta (`ajCsv`). `qtd` continua
   reaproveitando o MESMO seletor fixa/dinâmica da TASK-045 (lista não é incompatível com soma
   dinâmica, diferente do ativo dinâmico da TASK-046).
6. Exemplo exato do pedido do usuário: `{"acao": "adicionar_ativo", "tabela": "outros", "ativo":
   ["90525", "90542", "92540"], "qtd": -1}`.

## Restrições

- [x] Nenhum dos contratos listados em `RULES.md` (Regra 5) muda.
- `adicionar_ativo` continua restrito a Outros (`SO_OUTROS`).
- Nenhuma mudança em `regras_dominio.py`.
- Lista de ativos NÃO combina com ativo dinâmico (são modos mutuamente exclusivos de `ativo`); lista
  SIM combina com `qtd` dinâmico (diferente do ativo dinâmico da TASK-046, que só aceita `qtd` como
  fator).

## Critérios de aceite

- [x] `["90525", "90542", "92540"]` com `qtd: -1` adiciona os três, cada um com `*1-<código>`.
- [x] Sem `qtd` (padrão 1), cada código recebe quantidade 1.
- [x] `qtd` dinâmico (`{"soma": ...}`) aplica a MESMA soma a todos os códigos da lista.
- [x] Soma dinâmica zero não adiciona nada (mesmo comportamento do caso de ativo único).
- [x] `se_ja_existe: "somar"` funciona por código, inclusive quando só parte dos códigos já existe
  na linha.
- [x] Validação rejeita lista vazia, item com espaço/vazio, e aplica a mesma validação de `qtd` do
  caso de ativo único (reaproveitada via helper `_validar_qtd_adicionar`, sem duplicação).
- [x] `descrever_acao()` gera frase em português correta para lista (qtd fixa e qtd dinâmica).
- [x] UI: alternar "ativo" para "lista de códigos" mostra o campo certo e produz o JSON esperado
  (confirmado via Playwright).
- [x] Documentação `.ai` atualizada conforme `RULES.md` Regra 9.
- [x] `STATE.md` atualizado conforme `RULES.md` Regra 10.
