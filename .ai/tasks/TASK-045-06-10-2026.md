# TASK-045-06-10-2026

**`adicionar_ativo` aceita quantidade dinâmica (mesma quantidade de outro ativo da linha, com fator)**

> Pedido do usuário (dentro de um contexto, TASK-044): "se tem U3 adicione em mesma quantidade 90277
> negativo" — a quantidade do ativo adicionado deve igualar a quantidade de U3 encontrada NAQUELA
> linha (que varia: pode ser `1-U3`, `2-U3`, `3-U3`...), não um número fixo. Implementada em
> 2026-10-06.

## Objetivo

Permitir que `adicionar_ativo` use uma quantidade **dinâmica** — soma das quantidades de outro(s)
ativo(s) presentes na MESMA linha (via seletor, inclusive `@GRUPO`), multiplicada por um fator
opcional (ex.: `-1` para gerar o prefixo `"*"`/linha viva) — em vez de só um número fixo no JSON.

## Contexto

`services/ajustes_planilhas.py::_t_adicionar_ativo` lia `qtd` como um número literal
(`a.get("qtd", 1)`); a validação (`_validar_acao`) exigia `_numero_ok(qtd) and qtd != 0`. Não havia
forma de dizer "a mesma quantidade de X" — cada linha podia ter uma quantidade diferente de U3, e
um `qtd` fixo no cadastro da regra não acompanharia isso.

Confirmado com o usuário antes de implementar: U3 **pode** variar (`1-U3`, `2-U3`, `3-U3`...), não é
sempre 1 — então um `qtd` fixo não resolveria o pedido de verdade; era preciso uma capacidade nova
no motor.

Peça já existente reaproveitada: `services/regras_dominio.py::_cond()` já calcula
`soma(SELETOR)` para condições de validação (`{"soma": SEL, "qtd": CMP}`) — a mesma soma de
quantidades por seletor numa linha, só que ali usada para COMPARAR, não para gerar um valor. E
`services/ajustes_planilhas.py::_contexto(tabela, texto, grupos)` já constrói um `_Linha` (mesmo
objeto que `_cond` usa) a partir do texto de QUALQUER linha de Outros — já é chamado por `_quando()`
para avaliar a condição `quando` de cada ação.

## Situação atual (antes desta tarefa)

- `adicionar_ativo.qtd` só aceitava um número fixo, diferente de zero.
- `descrever_acao()` e a UI (`static/painel_ajustes.js`) só sabiam mostrar/editar um número.

## Comportamento desejado

1. `qtd` passa a aceitar, além de número: `{"soma": SELETOR, "fator"?: número}` — a quantidade final
   é a soma das quantidades dos itens da PRÓPRIA linha que casam com `SELETOR` (código, curinga,
   `@GRUPO`, lista, regex — mesma linguagem de seletor de sempre), multiplicada por `fator`
   (padrão 1). `fator: -1` gera o prefixo `"*"` automaticamente (mesma regra de sinal que já existia
   para `qtd` fixo negativo, TASK-038).
2. Soma dinâmica igual a zero (seletor não casou nessa linha) não adiciona nada — tratado como
   no-op, não como erro.
3. `descrever_acao()` descreve a quantidade dinâmica em português: `"adicionar '90277' na mesma
   quantidade de U3 (negativa) à linha..."`.
4. UI (`painel_ajustes.js`): novo seletor "quantidade": `fixa` (comportamento de sempre) ou
   `mesma quantidade de outro ativo` — nesse segundo modo, aparecem os campos "soma de" (seletor,
   mesmo autocomplete/formato de `remover_ativo`) e "fator" (número, dica "-1 = negativo
   (retirada)").
5. Exemplo exato do pedido do usuário: `{"acao": "adicionar_ativo", "tabela": "outros",
   "ativo": "90277", "qtd": {"soma": "U3", "fator": -1}, "quando": {"tem": "U3"}}`.

## Restrições

- [x] Nenhum dos contratos listados em `RULES.md` (Regra 5) — formato `<qtd>-<ativo>` de Outros não
  muda; só o JSON de CADASTRO da ação ganhou uma forma alternativa para `qtd`.
- `adicionar_ativo` continua restrito a Outros (`SO_OUTROS`) — a soma dinâmica também só lê a
  própria linha de Outros (via `_contexto`), nunca Cabos nem outras linhas.
- Nenhuma mudança em `services/regras_dominio.py` (reaproveitado só por leitura/composição).

## Critérios de aceite

- [x] `{"soma": "U3", "fator": -1}` numa linha com `N-U3` adiciona `*N-<ativo>` (prefixo `*`,
  magnitude = N).
- [x] Sem `fator` (padrão 1), a quantidade fica positiva, igual à soma.
- [x] `fator` diferente de 1/-1 multiplica a soma corretamente.
- [x] Soma zero (seletor não casa na linha) não altera a linha.
- [x] Soma com `@GRUPO`/seletor que casa mais de um item soma todos.
- [x] `se_ja_existe: "somar"/"substituir"` continua funcionando com quantidade dinâmica.
- [x] Validação rejeita `qtd` que não é nem número nem `{"soma": SELETOR, "fator"?: número}` válido
  (seletor/`@GRUPO` inexistente, campo desconhecido, `fator` não numérico).
- [x] `descrever_acao()` gera frase em português correta para quantidade dinâmica.
- [x] UI: alternar "quantidade" para dinâmica mostra os campos certos e produz o JSON esperado
  (confirmado via Playwright).
- [x] Documentação `.ai` atualizada conforme `RULES.md` Regra 9
- [x] `STATE.md` atualizado conforme `RULES.md` Regra 10

## Riscos

- Reaproveitar `_contexto()`/`_casa()` para a soma dinâmica depende de `extrair_ativos_outros`
  continuar devolvendo `{ativo, qtd}` já em maiúsculas (mesma suposição que `_cond`'s `soma` já
  fazia) — nenhuma mudança nesse contrato nesta tarefa.
- Um teste inicial usou um seletor hifenado (`@GRUPO` com código `SUP-L`) combinado a quantidade
  dinâmica negativa e expôs um guard de contrato PRÉ-EXISTENTE (`C1-OUT-NUM`) que trata mal códigos
  com hífen junto de um token `"*"` — confirmado como já existente antes desta tarefa (reproduz
  igual com `qtd` fixo negativo), não corrigido aqui (fora do escopo deste pedido); o teste foi
  ajustado para um seletor sem hífen (`@CHAVES`, `CFU`/`CFUR`).
