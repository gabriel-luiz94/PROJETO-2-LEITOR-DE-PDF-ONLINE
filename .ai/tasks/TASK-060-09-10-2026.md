# TASK-060-09-10-2026

**Modelos de obra: ativo variável com lista de opções — `V(quantidade)-X(ativo1,ativo2,ativo3)`**

## Objetivo

Hoje o modelo (TASK-058) só varia **quantidades** (`V`, `V(nome)`). Esta tarefa permite que o **ativo** também seja variável: no lugar do código do ativo o criador escreve `X(U3,U4,U5)` e, ao usar o modelo, a janela **Parâmetros do modelo** mostra um **dropdown** só com essas opções. Exemplo do pedido: `V(quantidade)-X(ativo1,ativo2,ativo3)` → o usuário informa a quantidade (número) e escolhe o ativo (lista).

## Contexto

Evolução da TASK-058 (modelos). Reaproveita: detecção/geração pura em `services/modelos_obra.py`, janela de parâmetros, bloqueio de Montar Orçamento, exportar/importar (056), regra `C1-VAR`.

## Situação atual

- `V` / `V(nome)` só valem como **quantidade** em Outros (`V-U4`, `*V-CFU`) e como **comprimento** em Cabos (`CAA 2 ABC V m`). O código do ativo é sempre fixo no modelo.
- Para ter "U3 ou U4 ou U5" hoje é preciso criar um modelo por variação.
- Os parâmetros ficam em `dados_json.modelo.parametros` (`chave`, `rotulo`, `padrao`); a janela só tem campos numéricos.

## Comportamento desejado

1. **Sintaxe** (só em **Outros**; um item é `<qtd>-<ativo>`, e agora qualquer das duas partes pode ser variável):
   - ativo variável: **`X(A,B,C)`** — lista de **2 a 30** opções, separadas por vírgula; ex.: `V-X(U3,U4,U5)`, `*V(qtd)-X(CFU,CFUA)`, `2-X(U3,U4)` (quantidade fixa, ativo variável) e `V(postes)-X(DT11/300,DT9/150)`.
   - `V(quantidade)` do exemplo é o `V(nome)` que já existe (nome do campo = "quantidade").
   - **Nomeado e compartilhado:** `X(poste:DT11/300,DT9/150)` define o campo "poste"; as demais ocorrências escrevem só `X(poste:)` e usam a **mesma escolha** (como `V(nome)` já faz). Sem `:` = um campo por ocorrência.
   - O `*` na frente continua sendo o sinal negativo escolhido pelo modelo.
   - Só é variável o formato exato `X(...)` com lista; `X`, `X9`, `1-X` ou `CAX(…)` **não** são.
2. **Salvar como modelo:** a janela lista os campos de **ativo** (rótulo, as opções vindas da sintaxe e, opcionalmente, uma opção **padrão**) junto dos de quantidade. As opções são validadas ao salvar: sem repetidas, só códigos de ativo válidos (sem espaço, `-`, `,`, `:`, parênteses).
3. **Usar o modelo** (Carregar / Adicionar / Subtrair e comando da IA): a janela mostra, para cada campo de ativo, um **`<select>`** com as opções (+ "— escolha —" quando não há padrão); **Gerar obra** só habilita com todas as escolhas feitas. O servidor confere que o valor é **uma das opções** (nunca texto livre) e gera a linha padrão, ex.: `3-U4`.
4. **Proteções:** `X(...)` que sobrar nas tabelas bloqueia **Montar Orçamento** e a validação acusa (`C1-VAR`: "variável de ativo sem escolha"); o resultado gerado continua passando pela camada 1.
5. **Exportar/importar** modelos leva `tipo` e `opcoes` dos parâmetros; o importado valida o mesmo.
6. **Compatibilidade:** modelos já salvos (só com `V`) não mudam e continuam funcionando.

## Restrições

- Sem mudança de schema do Supabase (os parâmetros vivem no `dados_json`).
- Contrato de ativos (Regra 5) **não muda**: depois de gerada, a linha é `<qtd>-<ativo>` comum.
- A IA continua **não** escolhendo valores (a janela é do usuário); o prompt só passa a dizer que o modelo também pode ter escolha de ativo.
- Regex do frontend (bloqueio do orçamento) espelha o backend (Regra 4).
- Chaves novas não podem colidir com as existentes (`#n` e nomes de quantidade): campos de ativo usam o prefixo `ativo:` (`ativo:poste`, `ativo:#1`).
- Testes isolados da nuvem.

## Exemplos

Modelo "Ponto de iluminação": Outros `V(qtd)-X(luz:LED50,LED100,LED150)` e `1-X(luz:)` (mesma escolha). O usuário B escolhe **LED100** e informa **3** → gera `3-LED100` e `1-LED100`. O modelo continua intacto.

## Riscos

- **Ambiguidade da sintaxe:** `X(nome:)` (referência) × lista de uma opção só; por isso a lista exige ≥ 2 opções e a referência exige `:`.
- **Opção que não existe na base de ativos:** o orçamento acusaria "não encontrado" só no fim (ver decisão 4).
- **Listas enormes** deixam o dropdown e a linha do modelo ilegíveis (limite de 30).
- **Dependência entre campos** (a quantidade depender do ativo escolhido) fica **fora** desta tarefa.

## Plano de teste

pytest (detecção, geração, validação, API, exportação/importação, compatibilidade com modelos antigos, mutações nos pontos críticos) e Chromium com dois usuários (criar, escolher no dropdown, gerar, desfazer, bloqueio de orçamento com `X(...)` sobrando).

## Decisões a confirmar com o usuário

1. **Sintaxe:** `X(A,B,C)` para o ativo; campo compartilhado por nome `X(poste:A,B)` + `X(poste:)`; `V(quantidade)` = o `V(nome)` que já existe. *(Recomendado: sim.)*
2. **Onde vale:** só **Outros** nesta tarefa. Em **Cabos** o ativo é um prefixo com espaço (`CAA 2`), então ficaria para uma tarefa própria. *(Recomendado: só Outros.)*
3. **Origem das opções:** só a lista escrita no modelo, **ou** também aceitar grupos do projeto (`X(@POSTES)` expande para os ativos do grupo). *(Recomendado: lista escrita + grupos `@`, pois os grupos já existem nas regras.)*
4. **Conferência das opções com a base de ativos do projeto ao salvar:** **avisar** (não impede salvar) / impedir / não conferir. *(Recomendado: avisar.)*
5. **Padrão:** a opção padrão é opcional; sem padrão o usuário **precisa escolher** (nada vem pré-selecionado). *(Recomendado: sim.)*
