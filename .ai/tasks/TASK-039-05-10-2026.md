# TASK-039-05-10-2026

**Reconexão automática do cliente Supabase após falha de rede (reativa)**

> Parte 1 de 3 do pedido do usuário "garantir que os dados estejam sempre disponíveis", junto com
> TASK-040 e TASK-041. Implementada em 2026-10-05.

## Objetivo

Fazer o processo se recuperar sozinho quando a conexão com o Supabase cair por timeout/queda de
rede, em vez de ficar permanentemente preso ao cliente "morto" até o processo ser reiniciado.

## Contexto

Usuário relatou: "a conexão com o Supabase está se perdendo após um tempo [de inatividade]". Achado
confirmado no código (não suposição):

- `services/supabase_client.py:13-52` — `get_supabase()` é um singleton de processo: cria o
  `Client` (e o `httpx.Client`/pool HTTP por baixo) **uma única vez**, protegido por
  `threading.Lock`, e devolve sempre o mesmo objeto depois disso (linha 26-27). Existe
  `reset_supabase_client()` (linha 55-60) que zera o singleton, mas **nenhum lugar do projeto a
  chama** — nem em erro, nem em retry.
- O padrão `except Exception: pass` está replicado em `routers/obras.py`, `recs.py`, `projetos.py`
  e `admin.py` (confirmado: 28 ocorrências nesses 4 arquivos). Uma falha de rede é tratada
  exatamente como "Supabase não configurado" — sem log, sem reset, sem retry.
- Resultado: se o Supabase (PostgREST/pgbouncer) fecha uma conexão ociosa do lado dele — comportamento
  normal desse tipo de serviço depois de alguns minutos sem uso —, a primeira chamada seguinte falha,
  é engolida, e **todas as chamadas depois repetem o mesmo cliente morto**, até reiniciar o processo.
- `GET /api/health` (`routers/health.py:50-66`) já expõe `supabase_configured`/`supabase_reachable`/
  `supabase_error` — é a ferramenta de diagnóstico certa, mas essa própria chamada usa o mesmo
  `get_supabase()` singleton e não força reconexão.

## Situação atual

Nenhum código chama `reset_supabase_client()`. Uma vez que uma chamada falhe por motivo de rede, o
sistema nunca mais tenta reabrir a conexão sozinho.

## Comportamento desejado

1. Criar um wrapper central (ex.: `services/supabase_client.py:executar_supabase(fn)` ou um
   decorator) que envolve toda chamada Supabase: se a chamada levantar uma exceção que pareça de
   rede/conexão (timeout, connection reset, broken pipe — não erro de autenticação/permissão/
   dados), chama `reset_supabase_client()` antes de propagar/engolir o erro, para que a **próxima**
   chamada (do mesmo request ou de um request futuro) crie um cliente novo.
2. Logar (nível `warning`, uma vez por ocorrência, sem spam) quando isso acontecer — hoje é 100%
   silencioso.
3. Não mudar o comportamento de fallback para SQLite que já existe (continua sendo o *catch* de
   último recurso) — só garantir que a *tentativa* seguinte tenha uma chance real de sucesso, em
   vez de repetir a mesma falha para sempre.
4. **Decisão tomada na implementação:** em vez de só uma defesa (reativa OU proativa), as duas
   foram combinadas, por serem complementares e de baixo risco: (a) **TTL proativo** — o cliente se
   recria sozinho depois de 180s, mesmo sem nenhuma falha observada, porque não há garantia de que
   o lado do Supabase/PostgREST não tenha fechado a conexão antes de qualquer chamada nova
   acontecer; (b) **reset reativo** — `registrar_falha()` (TASK-039+041, ver detalhe na TASK-041)
   reseta o cliente imediatamente quando a exceção parece ser de rede (`httpx.TransportError`/
   `httpx.TimeoutException`/`ConnectionError`/`OSError`/`TimeoutError`), nunca em erro de
   autenticação/dados. `registrar_falha()` é chamada nos 16 pontos de chamada reais a Supabase em
   `obras.py`/`recs.py`/`projetos.py`/`admin.py` (ver TASK-041 para a lista completa) — a decisão de
   "aplicar em todos" do item 4 original foi tomada.

## Restrições

- [x] Nenhum dos contratos listados em `RULES.md` (Regra 5).
- Não alterar o formato de retorno das rotas existentes nem o comportamento quando o Supabase
  realmente não está configurado (continua retornando `None`/fallback silencioso, isso é esperado).

## Critérios de aceite

- [x] Uma falha de rede numa chamada Supabase (simulada em teste, ex.: mock levantando
  `httpx.ConnectError`/`ConnectionResetError`) causa reset do cliente singleton.
- [x] A chamada seguinte (mesmo teste) cria um cliente novo (verificável comparando `id()` do objeto
  antes/depois, ou via mock contando chamadas a `create_client`).
- [x] Uma falha de autenticação/permissão/dados (ex.: RLS, chave inválida) **não** causa reset
  (resetar não ajudaria nesse caso e esconderia o erro real).
- [x] `GET /api/health` continua funcionando igual quando o Supabase está genuinely fora do ar.
- [x] Documentação `.ai` atualizada conforme `RULES.md` Regra 9
- [x] `STATE.md` atualizado conforme `RULES.md` Regra 10

## Arquivos afetados

- `services/supabase_client.py` — TTL de 180s em `get_supabase()`, `_eh_erro_de_rede()`,
  `registrar_falha()`.
- `routers/obras.py`, `recs.py`, `projetos.py`, `admin.py` — os 16 `except Exception: pass`
  silenciosos que envolvem chamadas reais ao Supabase agora chamam `registrar_falha(contexto, e)`.
- `tests/test_supabase_client.py` (novo, 14 testes).

## Riscos

- Detectar "é erro de rede" por tipo de exceção da lib `supabase-py`/`httpx` precisa ser específico
  o bastante para não resetar o cliente à toa em erros de dados/permissão (o que mascararia um
  problema real de RLS/schema como se fosse rede).
- Resetar o cliente no meio de um request que já está usando a referência antiga não quebra nada
  (a referência local continua válida até o fim daquele request; só a PRÓXIMA chamada a
  `get_supabase()` pega o novo).

## Plano de teste

`tests/test_supabase_client.py` (14 testes, todos passando): cliente mockado simulando (1) sucesso
normal com reaproveitamento dentro do TTL, (2) expiração de TTL recriando o cliente, (3) erro de
rede (`httpx.ConnectError`/`ConnectTimeout`/`ReadTimeout`/`ConnectionError`/`TimeoutError`)
resetando o cliente, (4) erro de dados/autenticação (`ValueError`/`KeyError`) **não** resetando,
(5) log sempre emitido em `registrar_falha`, mesmo sem reset, (6) sem credenciais não cria cliente
nem expira. Suíte completa do projeto (699 testes) reexecutada ao final sem regressões. Sem teste
de integração real contra um Supabase de verdade (fora do escopo/CI deste projeto).
