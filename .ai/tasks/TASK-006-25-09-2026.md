## Objetivo

Transformar as regras do leitor de PDF/DXF que fazem a classificação (entidade, operação, ativo)
em uma tabela de regras editável, visível e separada por projeto — hoje essa lógica está embutida
no código.

## Contexto

Hoje as regras do leitor estão implícitas no código. O objetivo é transformar essas regras em uma
tabela onde podem ser vistas, editadas e replicadas entre projetos.

## Situação atual

Ao ler um projeto, o programa realiza a classificação usando as regras presentes no código. Não é
possível ver, editar ou adaptar essas regras de projeto para projeto.

## Comportamento desejado

Na aba do leitor haverá um botão "REGRAS DO LEITOR", um indicador do projeto selecionado (mesmos
já cadastrados) e as regras de cada projeto.

## Restrições

O resultado da classificação precisa continuar igual ao atual.

## Critérios de aceite

- Ao clicar no botão "Regras do Leitor", ele mostra as regras do leitor usadas para o projeto
  selecionado.
- Se o projeto selecionado não tiver nenhuma regra cadastrada, o sistema avisa e pergunta se o
  usuário quer usar as regras de outro projeto para aquela leitura; se sim, ele escolhe o projeto
  de origem e o processamento/classificação roda com as regras desse projeto (decidido em
  refinamento, 2026-09-25 — ver "Diagnóstico preliminar" abaixo).

## Exemplos

### Entrada

Projeto Paraíba tem cadastrada a "regra 1".

### Resultado esperado

Ao selecionar o projeto Rondônia, a "regra 1" não aparece, porque não foi cadastrada nesse
projeto.

### Entrada (projeto sem regras)

Projeto Amazonas não tem nenhuma regra do leitor cadastrada. O usuário tenta ler um arquivo com o
projeto Amazonas selecionado.

### Resultado esperado

O sistema avisa que o projeto não tem regras e pergunta se deseja usar as regras de outro
projeto. O usuário escolhe "Paraíba"; a leitura é processada e classificada com as regras do
projeto Paraíba, só para essa leitura (as regras não ficam associadas ao Amazonas).

## Modelo de regras (refinamento, 2026-09-25 — fechado com o usuário)

Decisões tomadas nesta revisão, todas confirmadas pelo usuário:

- **Sincronização real com o Supabase** desde o início (não só local), no mesmo padrão de
  `regras_conversao` (TASK-003).
- **Unificar agora**, em vez de replicar as divergências: a nova tabela de regras passa a produzir
  um único comportamento canônico, baseado em `script.js` (a variante mais completa — inclui
  `01_ORCAMENTO`, `01_PARTICULAR`, cor azul e `BLOCO`+`TERRA3`, que `resumo.js` não tem). A partir
  da implementação desta tarefa, "resultado igual ao atual" passa a significar "igual ao
  comportamento hoje em `script.js`" — isso muda o resultado em alguns casos que hoje divergem
  entre as duas abas. **A nuance de cor do layer `01_ORCAMENTO` foi preservada** (2026-09-25): a
  cor continua sendo fator de entrada ali — vermelho e "demais cores" geram `I`, cinza gera `R`,
  igual ao `script.js` de hoje (ver "Exemplos" abaixo).
- **Duas tabelas encadeadas**, não uma só — proposta do usuário, mais limpa que a primeira
  proposta (uma cascata única): **Processamento** decide operação+ativo a partir de
  texto/cor/layer; **Classificação** decide entidade (e pode ajustar a operação) a partir do que a
  Processamento produziu, **mais** cor/layer/texto bruto de novo (para os casos que precisam
  desses sinais na hora de classificar, ex. `hasApoioConflict`). A Classificação é a mesma tabela
  reutilizável na aba Resumo (substitui `autoClassifyEntidade` diretamente).

### Tabela de Processamento

**Entrada:** texto bruto, cor, layer (+ vizinhança de linhas, opcional) · **Saída:** operação,
ativo

| Campo | Descrição |
|---|---|
| `projeto_codigo`, `ordem`, `ativa`, `descrição` | metadados de toda regra |
| `cor` | `VERMELHO` / `CINZA` / `PRETO` / `AZUL` / `QUALQUER` |
| `layer_em` | lista de layers aceitos, ou vazio = qualquer |
| `texto_regex` | regex sobre o texto bruto extraído |
| `vizinhanca` *(opcional)* | `{regex, janela (nº de linhas), mesma_página}` → captura um valor da(s) linha(s) vizinha(s) da mesma página, disponível no template de saída (único uso hoje: elo fusível) |
| → `operacao` | valor fixo (`I`/`R`/`M`/`*I`/...), `PELA_COR` (vermelho→I, cinza→R, resto→M), `0` (linha ignorada) ou vazio (deixa a Classificação decidir) |
| → `ativo_template` | reescreve o ativo usando capturas de `texto_regex`/`vizinhanca` (ex. `{1}-CFU {1}-EF{2}`), ou `MANTÉM` |
| → `parar` | `true` encerra a cascata de Processamento aqui; `false` continua avaliando as próximas regras (necessário para os overrides incondicionais de layer) |

### Tabela de Classificação

**Entrada:** operação, ativo (já processados), cor, layer, texto bruto · **Saída:** operação
(ajustada), entidade · **reutilizável na aba Resumo**

| Campo | Descrição |
|---|---|
| `projeto_codigo`, `ordem`, `ativa`, `descrição` | metadados |
| `operacao_em` | lista de operações aceitas, ou vazio = qualquer |
| `ativo_regex` | regex sobre o ativo processado |
| `cor` / `layer_em` | mesmo formato da tabela de Processamento |
| `texto_regex` | regex sobre o texto bruto (ex.: para bloquear falso-positivo de APOIO quando o texto tem "APOIOS" no plural) |
| → `entidade` | valor fixo, ou **não definido** (regra só controla o fluxo, não classifica nada) |
| → `operacao_ajustada` *(opcional)* | sobrescreve a operação — é aqui que entra, por exemplo, a "força operação I" para entidades IP/APOIO/CERCA/RAMAIS: cada regra que atribui uma dessas entidades já define `operacao_ajustada = I` junto, em vez de um passo separado |
| → `parar` | `true` encerra a Classificação aqui (com ou sem `entidade` definida — uma regra de bloqueio usa `entidade` vazio **e** `parar = true` para impedir uma regra de prioridade menor de classificar a linha, sem ela mesma classificar como outra coisa); `false` continua avaliando |

### Regras de motor (comportamento do engine, não são linhas de tabela)

- `operação == "0"` (saída da Processamento) → a linha **não passa** pela Classificação; entidade
  fica `0` (equivalente ao layer `01_PARTICULAR` hoje).

O layer `01_ORCAMENTO`/`01_ORCAMENTO_LV` **não precisa mais de mecanismo especial de motor** —
como a Classificação também recebe cor e layer, ele vira duas regras normais (ver exemplo abaixo):
regras de Processamento que calculam a operação pela cor (preservando a nuance cinza→R), e uma
regra de Classificação de prioridade máxima que usa `layer_em` para produzir `entidade = AVULSO`.

### Exemplos já mapeados do código atual

**Regras de Processamento** (combo chave fusível + elo fusível):
`cor=QUALQUER`, `texto_regex=/([13])\s*-\s*100A\s*-\s*(\d+(?:,\d+)?[HK])/i` →
`operacao=PELA_COR`, `ativo_template="{1}-CFU {1}-EF{2}"`, `parar=true`.
Entrada `"1 - 100A - 1H"` (cor vermelha) → saída: operação `I`, ativo `"1-CFU 1-EF1H"`.

**Regras de Processamento + Classificação** (layer `01_ORCAMENTO`, com cor preservada):
- Processamento, prioridade alta: `layer_em=[01_ORCAMENTO]`, `cor=CINZA` → `operacao=R`,
  `ativo=MANTÉM`, `parar=true`.
- Processamento, prioridade logo abaixo: `layer_em=[01_ORCAMENTO]`, `cor=QUALQUER` (pega
  vermelho e as demais cores) → `operacao=I`, `ativo=MANTÉM`, `parar=true`.
- *(mesmo par de regras repetido para `01_ORCAMENTO_LV`, com `operacao=*R`/`operacao=*I`)*
- Classificação, prioridade máxima: `layer_em=[01_ORCAMENTO, 01_ORCAMENTO_LV]` → `entidade=AVULSO`,
  `parar=true` (a operação não precisa de `operacao_ajustada` aqui — a Processamento já calculou
  o valor certo, com a cor considerada).

**Regras de Classificação** (roço vira APOIO, com bloqueio de conflito):
1. *(guarda, prioridade mais alta)* `ativo_regex=/-ROCO/`, `texto_regex=/APOIOS/` (ou `LARGURA`, ou
   `BASE`+`CALÇADA`) → `entidade` não definido, `parar=true` — impede a regra 2 de rodar quando o
   texto bruto sinaliza conflito, sem classificar a linha como outra coisa (fica como estava).
2. *(caso normal)* `ativo_regex=/-ROCO/` → `entidade=APOIO`, `operacao_ajustada=I`, `parar=true`.

## Implementação (2026-09-25)

O modelo acima foi refinado mais uma vez durante a implementação, a pedido do usuário: em vez de
deixar `processAtivoFormula` como código fixo (minha recomendação original), **ela também virou
regras editáveis** — exigiu estender a Tabela de Processamento com um conceito de **fases** e um
segundo modo de regra (`SUBSTITUIR`), além do `DEFINIR` já descrito acima:

- **Fase 1 — seleção de ramo** (evita `processAtivoFormula`, parte 1): mesmas regras `DEFINIR` já
  descritas, mas agrupadas numa fase que para na primeira que casar (replica o `if/else if`
  original) sem impedir as fases seguintes de rodar.
- **Fase 2 — pós-processamento** (`processAtivoFormula`, parte 2): regras em modo `SUBSTITUIR`
  (casam contra o **ativo já calculado pela fase 1** e aplicam um `String.replace` nativo do JS —
  sintaxe `$1`, `$2` no template) ou `SUBSTITUIR_TOTAL` (substitui o ativo inteiro e encerra a
  fase — usado só no caso "combo `100A`", que no código original também encerra
  `processAtivoFormula` antecipadamente).
- **Fase 3 — overrides por cor/layer** (`updateRowLogic`): as regras já descritas acima (elo
  fusível, FLY, `BLOCO`+`TERRA3`, reinstalação, `01_ORCAMENTO`).

Com isso, a **tabela de Processamento cobre 100% do que antes estava em código** — nada ficou
fixo, incluindo a normalização de texto. `.ai/CONTEXT.md` e `.ai/ARCHITECTURE.md` ainda precisam
ser atualizados para refletir essa mudança de arquitetura (pendente — ver "Não corrigido nesta
etapa" abaixo).

### Dois bugs reais encontrados no código original (decisão do usuário: corrigir, não replicar)

Durante a validação por paridade (ver "Testes" abaixo), a comparação entre o motor novo e uma
porta fiel do `updateRowLogic` original revelou dois bugs pré-existentes em `script.js`:

1. **Elo fusível nunca virava `CHAVE` automaticamente.** A variável `uAtivo` (usada por toda a
   cascata de classificação) era calculada **antes** do bloco do elo fusível reescrever o ativo via
   busca na vizinhança — a reescrita só afetava o `textoAtivo` final, não a variável usada para
   classificar. Resultado: mesmo achando a quantidade certa na vizinhança, a linha nunca era
   classificada como `CHAVE`.
2. **Detecção de cabo multiplexado (`M3x1`) nunca funcionava.** A regex `/\bM?\d+x\d+/` usa `x`
   minúsculo sem flag *case-insensitive*, mas era testada contra o texto já em maiúsculas — nunca
   podia casar.

**Decisão do usuário (2026-09-25): corrigir os dois** no motor novo, em vez de replicar os bugs.
Confirmado via teste automatizado que o motor agora classifica corretamente esses dois casos.

### Correção de convenção: `projeto_codigo` é o código, não o nome

Mesmo problema identificado e corrigido na TASK-005 (ver lá): o seed inicial das regras foi escrito
por engano usando os *nomes* dos projetos (`"PARAIBA"`/`"RONDONIA"`) como chave, quando a convenção
real do app (`regras_conversao`, `localStorage['projeto_selecionado_codigo']`) é o *código*
(`"027"`/`"229"`). Descoberto durante o teste end-to-end no navegador real (Playwright): o seletor
de projeto carregava, mas as regras vinham sempre vazias porque a busca usava o código e o seed
usava o nome. Corrigido em `database.py:_seed_regras_leitor`.
