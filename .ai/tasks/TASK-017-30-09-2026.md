# TASK-017-30-09-2026

## Objetivo

Editor **visual e legível** das regras de domínio no painel admin: a regra é montada e lida em frases em português, com
seletores de ativo e de quantidade, sem exigir JSON nem regex; o JSON fica como modo avançado.

## Contexto

Camada 2 do ADR-004. Depende da TASK-016 (linguagem v2, `descrever`, `explicacao`) e complementa a TASK-018 (regras por
projeto). Pedido do usuário (2026-09-30): regras "mais legíveis".

## Situação atual

`static/admin.html`/`admin.js` (TASK-013): cada regra é um cartão com caixa "ligada", id, tipo, severidade, mensagem,
operações e um **textarea de JSON** com regex. Trocar o tipo zera os parâmetros. Não há nenhuma pista do que a regra
faz sem ler a regex; o painel de teste só diz "achado / não achado", sem o motivo.

## Comportamento desejado

1. **Cartão em frase:** a regra aparece como texto legível gerado por `descrever(regra)`, por exemplo:
   *"Em cada linha de **instalação** de **Outros**: se tiver **CFU** com quantidade **= 1**, então deve ter **SUPL** com
   quantidade **≥ 1**. Gravidade: **aviso**."* Clicar em uma parte abre o campo daquela parte.
2. **Construtor de condições:** linhas "SE / ENTÃO / EXCETO SE" com seletor de ativo, comparador de quantidade e número;
   botões "E" / "OU" / "NÃO" para combinar; sem digitar regex.
3. **Seletor de ativo com ajuda:** autocomplete dos códigos da base técnica e dos **grupos** (`@ESTRUTURA_MT`), com
   curinga; regex só no modo avançado.
4. **Editor de grupos:** criar/renomear/editar grupos (com aviso de quais regras usam cada grupo) — mudar o grupo muda
   todas as regras que o usam.
5. **Modo avançado:** alternar para o JSON da regra (validado como hoje); alternar de volta reescreve a frase.
6. **Painel de teste explicativo:** para cada achado mostra a `explicacao` ("a linha tem 1-CFU e não tem SUPL") e, para
   linhas que **não** dispararam, dá para pedir "por que não?" (qual condição não foi satisfeita).
7. **Nova regra guiada:** "Adicionar regra" abre um assistente com modelos ("exigir X quando houver Y", "proibir X junto
   de Y", "mínimo de X por Y", "total da planilha") em vez do modelo JSON cru.
8. Preserva o que já existe: ligar/desligar, severidade, operações, histórico com reversão, restaurar/adicionar da semente.

## Restrições

- Nenhuma lógica de avaliação no frontend: a frase e a explicação vêm do backend (`descrever`/`explicacao`) para não
  criar mais uma cópia de regra de negócio (RULES Regra 4).
- Conteúdo sempre inserido por `textContent`/`value` (nunca `innerHTML`).
- Só admin escreve; operador continua só lendo (as rotas já garantem).
- Contratos (Regra 5): [x] Nenhum dos contratos listados.

## Critérios de aceite

- [x] Todas as 11 regras da semente aparecem como frases corretas, sem mostrar regex
- [x] Criar a regra "só `1-CFU` exige SUPL" pelo construtor, sem digitar JSON nem regex, e salvá-la
- [x] Editar um grupo atualiza a frase e o resultado de todas as regras que o usam
- [x] Modo avançado (JSON) ↔ visual sem perder informação
- [x] O painel de teste mostra a explicação do disparo e o "por que não?"
- [x] Verificado no navegador (fluxo completo) e sem erros de JS; `.ai` e STATE/CHANGELOG atualizados

## Exemplos

Entrada: usuário escolhe SE `CFU` `quantidade = 1` ENTÃO deve ter `SUPL` `≥ 1`, gravidade aviso.
Resultado esperado: frase acima + JSON v2 equivalente salvo; teste com `DT11/300 1-CFU` → "a linha tem 1-CFU e não tem SUPL".

## Arquivos potencialmente afetados

## Riscos

- Tela grande e complexa de manter sem framework: dividir em funções pequenas e cobrir com um roteiro de navegador.
- Regra montada no visual gerar v2 inválida: o backend valida no salvamento e devolve a lista de erros na tela.
- Aparência com estilo não pôde ser verificada até hoje (Tailwind por CDN bloqueado no ambiente de teste): usar CSS
  local para o editor ou avisar que o visual não foi conferido.
