# TASK-041-05-10-2026

**Visibilidade de falha de sincronização com a nuvem (gravação local garantida, erro nunca mais silencioso)**

> Parte 3 de 3 do pedido do usuário "garantir que os dados estejam sempre disponíveis. E em caso de
> perda de conexão os dados se mantenham com a última versão carregada para trabalho". Independente
> das TASK-039/040, mas junto elas fecham o pedido todo. Implementada em 2026-10-05.

## Objetivo

Confirmar (e corrigir onde faltar) que toda gravação continua **sempre** no SQLite local mesmo
quando o Supabase falha, e trocar o silêncio total (`except Exception: pass`, sem log, sem aviso)
por um registro visível — sem travar o uso do programa — para que ninguém descubra só depois que
alguma coisa não foi para a nuvem.

## Contexto

Ponto de partida: o próprio usuário já perguntou sobre a conexão instável com o Supabase (TASK-039/
040 tratam a causa). Esta tarefa é sobre a **consequência** para os dados: o que acontece com uma
gravação/leitura quando a falha ocorre.

Achado já confirmado por leitura de código (`routers/obras.py:99-122`, função `save_obra`): a
gravação **já** segue o padrão "tenta nuvem (engolindo erro) → sempre grava no SQLite → sempre
retorna sucesso":
```python
supabase = get_supabase()
if supabase:
    try:
        supabase.table("obras").upsert({...}).execute()
    except Exception:
        pass
conn = get_connection()
cursor.execute("INSERT OR REPLACE INTO obras (...) VALUES (...)", (...))  # SEMPRE roda
conn.commit(); conn.close()
return {"status": "success"}  # SEMPRE "success", mesmo se a nuvem falhou
```
Ou seja: o dado do usuário **não se perde** nesse caminho — ele sempre cai no SQLite local, que é
exatamente "a última versão carregada para trabalho" que o usuário pediu para preservar. O problema
real não é perda de dado, é **falta de aviso**: o `{"status": "success"}` mente sobre o estado da
sincronização, e o `except Exception: pass` não deixa rastro nenhum (nem log).

Esse padrão se repete em `routers/recs.py` (confirmado: 6 ocorrências de `except Exception` nos
handlers de leitura/escrita) e, pelo que o `.ai/STATE.md` já registra (item 21), também em
`projetos.py` e `admin.py`.

**Padrão melhor já existe no próprio projeto** (ADR-004/TASK-003, `routers/regras.py`,
`GET/POST /api/regras/conversao`): lá, a falha de sincronização com a nuvem **não é engolida** —
vira `HTTPException 500` visível ao usuário, com o dado já salvo localmente garantido antes. É
esse padrão que esta tarefa propõe generalizar.

## Situação atual

- Escrita: grava sempre local, mas mente "success" e não loga a falha de nuvem (`obras.py`,
  `recs.py`, provavelmente `projetos.py`/`admin.py` — precisa confirmar cada um na implementação).
- Leitura: cai para SQLite quando a nuvem falha (`if res.data is not None: return res.data`,
  senão continua para o bloco do SQLite) — **mas também sem log**, então não há nenhum jeito de
  saber, só olhando os dados, se o que a tela mostra veio da nuvem ou do cache local.

## Comportamento desejado

A definir em detalhe na implementação, mas o alvo:

1. **Nunca perder o aviso**: toda vez que uma chamada ao Supabase falhar (leitura ou escrita),
   logar pelo menos em nível `warning`, com o nome da rota/tabela e o erro. **Implementado** via
   `services/supabase_client.registrar_falha(contexto, exc)` (compartilhado com a TASK-039, que já
   decide se a falha também reseta o cliente singleton — centralizado num só lugar, sem log
   duplicado) chamado nos 16 pontos antes silenciosos.
2. **Escrita — decisão tomada:** opção **(a)** — mantido o comportamento atual (sempre grava local,
   sempre responde sucesso), só adicionando o log. Justificativa: menor risco, sem mudança de UX
   percebida pelo usuário, e o log em `warning` já resolve o problema real relatado ("não dá para
   saber o que está acontecendo"); a opção (b) (erro visível em toda escrita) foi deixada de fora
   por exigir que todas as telas que salvam obra/REC/projeto/usuário tratassem um novo erro sem
   travar o fluxo — mudança maior, não pedida explicitamente pelo usuário.
3. **Leitura**: optou-se por manter apenas o log (sem campo `"fonte": "cache_local"` na resposta) —
   suficiente para diagnóstico via log do servidor, sem alterar o contrato de resposta das rotas.
4. **Confirmado, sem necessidade de mudança de código**: o padrão existente
   `if res.data is not None: return res.data` (senão cai para o bloco do SQLite) já está correto —
   uma exceção real sempre pula essa linha e cai direto no fallback do SQLite; uma lista vazia
   genuína (`res.data == []`, sem exceção) é o único caso que "substitui" o SQLite, e isso é
   comportamento esperado (a nuvem respondeu, só não tinha dados), não uma falha disfarçada.

## Riscos

- Mudar de "sempre sucesso" para "erro visível quando a nuvem falha" (opção b) é uma mudança de
  comportamento perceptível pelo usuário — pode gerar mensagens de erro em cenários que hoje
  passam batido. Por isso o item 2 pede decisão explícita antes de implementar.
- Logar demais pode gerar ruído se a conexão cair com frequência (mitigar com log só na transição
  de estado, não a cada tentativa, se isso for feito junto com a TASK-040).

## Plano de teste

`tests/test_supabase_client.py` cobre `registrar_falha()` isoladamente (log sempre emitido, reset
condicional por tipo de exceção). A suíte completa dos routers afetados (`obras`, `recs`,
`projetos`, `admin`) foi reexecutada sem regressões — o comportamento de fallback para SQLite já
existente nesses testes continua validando que o dado nunca se perde. Sem teste de integração real
contra um Supabase de verdade.
