## Objetivo

Separar por projeto os itens salvos: obras salvas, RECs salvos, regras de IA (aprendizado) e
regras do leitor de PDF/DXF.

## Contexto

Hoje todos os itens salvos ficam visíveis em todos os projetos. O ideal é que cada item fique
disponível apenas no projeto em que foi salvo.

## Situação atual

Se o usuário salva uma obra do projeto Rondônia, ela também aparece quando ele está no projeto
Paraíba. O mesmo ocorre com os RECs salvos.

## Comportamento desejado

As obras salvas no projeto Rondônia ficam disponíveis apenas no projeto Rondônia; o mesmo vale
para RECs, regras de IA e regras do leitor.

## Restrições

Lógicas de salvamento, lógica de cálculo, etc. (não alterar).

## Critérios de aceite

Ao salvar uma obra do projeto Rondônia, ela não aparece quando o usuário está no projeto Paraíba.

## Exemplos

### Entrada

Salvei a obra 1 no projeto Paraíba.

### Resultado esperado

Ao selecionar o projeto Rondônia, ela não aparece.

## Diagnóstico preliminar (revisão — não é o plano de implementação)

Confirmado por leitura de código que, hoje, **nenhuma** das três tabelas envolvidas
(`obras`, `historico_rec`, `regras`) tem qualquer coluna de projeto — o filtro por projeto
precisará ser adicionado do zero em todas.

Achados/pontos que a implementação vai precisar resolver (nenhum decidido aqui, apenas
registrado para quando a tarefa for executada):

1. **"Regras do leitor de PDF/DXF" ainda não existe como dado salvo.** Hoje a classificação do
   leitor é feita por lógica embutida no JS (`static/script.js`/`static/resumo.js`), não por uma
   tabela de regras — não há nada para "separar por projeto" ainda nesse item específico. A
   TASK-006 (`.ai/tasks/TASK-006-25-09-2026.md`) é exatamente a tarefa que cria essa tabela, e já
   nasce com escopo por projeto. Recomendação a validar com o usuário no início da implementação:
   executar TASK-006 antes (ou junto) da parte de "regras do leitor" desta tarefa, já que uma
   depende da outra existir.
2. **"Regras de IA" (tabela `regras`, aprendizado usado em `ai_chat.py`) hoje só existe no SQLite
   local** — sem nenhuma sincronização com o Supabase (diferente de `regras_conversao`, corrigida
   na TASK-003). Antes de só "separar por projeto", vale confirmar com o usuário se essa tabela
   também deveria passar a ser compartilhada na nuvem (mesmo padrão da TASK-003), ou se
   separar-por-projeto deve valer só localmente por enquanto — pode mudar o escopo da tarefa.
3. `GET /api/recs` hoje retorna RECs de **todos os usuários**, não só do usuário logado (parece
   intencional — RECs parecem ser compartilhados entre usuários por design, ver
   `routers/recs.py:88-94`, onde salvar por cima de um REC de outro usuário cria uma cópia em vez
   de bloquear). Adicionar filtro por projeto não deve mudar esse comportamento de
   compartilhamento entre usuários, só restringir por projeto — mas vale confirmar que esse é o
   entendimento correto antes de implementar.
4. A restrição "lógicas de salvamento, lógica de cálculo, etc." não deve impedir adicionar um
   novo campo/coluna `projeto` ao que já é salvo (isso é inerente ao pedido) — a leitura mais
   provável é "não mude o que é calculado nem como os dados são estruturados além do necessário
   para o filtro por projeto". Confirmar esse entendimento antes de implementar, já que é uma
   restrição um pouco ampla.
5. Backfill de dados já existentes: obras e RECs salvos **antes** desta mudança não têm projeto
   associado. Precisa decidir (com o usuário) o que fazer com eles — aparecer em todos os
   projetos como hoje (fallback), ficar ocultos até serem editados, ou outra regra. A TASK-001
   já teve um caso real de efeito colateral de `DEFAULT` mal escolhido em `ALTER TABLE` (ver
   `STATE.md`, problema 8) — vale ter esse cuidado em mente aqui também.
