# TASK-044-06-10-2026

**Contextos dentro de um projeto (subconjuntos de Ajustes, com desenho genérico para Regras de Domínio depois)**

> Pedido do usuário: dentro do mesmo projeto (ex.: RONDONIA), poder cadastrar "contextos" (ex.: "obras
> de 34,5kV") — cada um com seu próprio conjunto de ajustes ligados/desligados/sobrescritos — e
> escolher o contexto ativo por um seletor na linha de totais (postes/cabos/equipamentos). Registrada
> em 2026-10-06; implementada em 2026-10-06.

## Objetivo

Acrescentar uma **terceira camada** de personalização, abaixo do overlay de projeto que já existe:
`padrão (DEFAULT) → overlay do projeto → overlay do contexto`. O "contexto" é nomeado, só existe
dentro de um projeto, e pode ligar/desligar ajustes, sobrescrever campos de um ajuste ou até
acrescentar ajustes exclusivos daquele contexto — mesmo poder que o overlay de projeto já tem hoje,
só numa granularidade mais fina.

## Contexto

Investigação confirmou (ver `.ai/CHANGELOG.md` desta data para o relatório completo):

- `services/ajustes_camadas.py::efetivo(padrao, overlay)` já resolve "padrão + overlay → lista
  efetiva", e **não sabe que só existe uma camada** — ela só recebe uma lista e um overlay. Pode ser
  chamada em cadeia sem mudar nada nela: `efetivo(efetivo(padrao, overlay_projeto)[0], overlay_contexto)`.
  Mesmo desenho existe em `services/regras_camadas.py` para as Regras de Domínio.
- Armazenamento hoje é uma linha por `projeto_codigo` (chave simples) em `ajustes_planilhas`/
  `regras_dominio`. Não há chave composta em lugar nenhum.
- Não existe hoje nenhum conceito de "contexto"/"cenário" como subconjunto de regras dentro do
  mesmo projeto — é funcionalidade nova, sem nada para migrar.
- UI: `#select-projeto` é uma "pill" no cabeçalho (label + `<select>` transparente), alimentada por
  `GET /api/projetos`. A linha de totais (`#resumo-rede-painel`, onde o usuário quer o seletor de
  contexto) é uma fileira flexível de cards, **100% calculada no cliente** a partir de
  `tableStates.cabos`/`tableStates.outros` — trocar de contexto não recalcula nada por si só.

Decisões do usuário (2026-10-06), depois de 3 perguntas sobre estratégia:
1. **Estratégia de dados**: overlay completo por contexto (não um simples mapa de liga/desliga) —
   mesmo poder do overlay de projeto, uma camada abaixo.
2. **Escopo**: desenhar genericamente agora, para que "contexto" também valha para Regras de
   Domínio no futuro, sem redesenho — mas a implementação desta tarefa cobre só **Ajustes**
   (Regras de Domínio fica para uma tarefa futura, reaproveitando o mesmo desenho).
3. **Comportamento da UI**: trocar o contexto no seletor só define qual conjunto de ajustes roda na
   próxima vez que o usuário clicar em "Ajustar" — não recalcula nada na hora (mesmo comportamento
   que qualquer ajuste já tem hoje: só afeta as tabelas quando efetivamente aplicado).

## Situação atual

- `ajustes_planilhas(projeto_codigo PK, ajustes_json)` — uma linha por projeto, sem noção de
  contexto.
- `routers/validacao_ajustes.py::resolver(projeto_codigo)` resolve só duas camadas (padrão +
  projeto).
- `#select-projeto` é o único seletor de escopo na tela; `#resumo-rede-painel` só tem 4 cards fixos
  de totais.

## Comportamento desejado

### 1. Modelo de dados (novas tabelas, nenhuma existente alterada)

```sql
-- Metadados de quais contextos existem por projeto — compartilhado entre mecanismos (hoje só
-- Ajustes consome; Regras de Domínio poderá reaproveitar esta mesma tabela no futuro).
CREATE TABLE contextos (
    projeto_codigo TEXT NOT NULL,
    contexto TEXT NOT NULL,              -- nome do contexto, é a própria chave (ex.: "34,5kV")
    criado_em TEXT DEFAULT (datetime('now')),
    criado_por TEXT,
    PRIMARY KEY (projeto_codigo, contexto)
);

-- Overlay de Ajustes específico de um contexto — mesmo shape de ajustes_camadas.py
-- ({"versao": 1, "overlay": true, "adicionadas": [...], "sobrescritas": {...}, "ocultas": [...]}).
CREATE TABLE ajustes_contextos (
    projeto_codigo TEXT NOT NULL,
    contexto TEXT NOT NULL,
    ajustes_json TEXT NOT NULL,
    updated_at TEXT DEFAULT (datetime('now')),
    PRIMARY KEY (projeto_codigo, contexto)
);
CREATE TABLE ajustes_contextos_historico (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    projeto_codigo TEXT NOT NULL,
    contexto TEXT NOT NULL,
    ajustes_json TEXT NOT NULL,
    criado_em TEXT DEFAULT (datetime('now')),
    criado_por TEXT
);
```
Espelhado em `scripts/schema_supabase.sql` (mesmo padrão de `DISABLE ROW LEVEL SECURITY` das
demais tabelas de regras/ajustes). `services/repo_json.py::RepoJson` é genérica o bastante para
`tabela`/`tabela_hist`/`coluna`, mas assume PK simples (`projeto_codigo`) — precisa de uma pequena
extensão (aceitar uma segunda coluna de chave opcional) ou de uma classe irmã enxuta
(`RepoJsonComposto`) só para `(projeto_codigo, contexto)`; decisão de implementação, não de produto.

### 2. Resolução em cadeia (zero mudança em `ajustes_camadas.py`)

```python
def resolver(projeto_codigo: str = DEFAULT, contexto: str | None = None):
    padrao = _padrao()
    overlay_projeto = None if projeto_codigo == DEFAULT else _overlay_do_projeto(...)
    efetivo_projeto, avisos1 = efetivo(padrao, overlay_projeto or overlay_vazio())
    if not contexto:
        return efetivo_projeto, avisos1, overlay_projeto, None
    overlay_contexto = _buscar_overlay_contexto(projeto_codigo, contexto)  # overlay_vazio() se não existir
    efetivo_final, avisos2 = efetivo(efetivo_projeto, overlay_contexto)    # MESMA função, chamada 2x
    return efetivo_final, avisos1 + avisos2, overlay_projeto, overlay_contexto
```
**Limitação aceita conscientemente**: como a 2ª chamada a `efetivo()` recebe a lista já anotada da
1ª como seu "padrão", o campo `origem` de cada ajuste no resultado final reflete só a relação com a
**última** camada (contexto), perdendo se o ajuste também foi sobrescrito no overlay de projeto.
Aceitável para a v1 — não bloqueia nenhum critério de aceite.

### 3. API (tudo com `contexto: str | None = None` opcional — **sem contexto, comportamento
   idêntico ao de hoje**, garantindo retrocompatibilidade total)

- `GET /api/validacao/ajustes/contextos?projeto_codigo=X` → lista de contextos do projeto.
- `POST /api/validacao/ajustes/contextos` `{projeto_codigo, contexto}` (admin) → cria um contexto
  novo com overlay vazio.
- `POST /api/validacao/ajustes/contextos/excluir` `{projeto_codigo, contexto}` (admin) → remove o
  contexto (overlay + metadado; não toca nos ajustes do projeto).
- `GET/POST /api/validacao/ajustes`, `/preview`, `/preview-lote`, `/historico`, `/reverter` ganham
  o campo opcional `contexto` — quando presente, leem/gravam o overlay do CONTEXTO em vez do
  overlay do projeto (o editor da aba Ajustes, ao abrir com um contexto selecionado, edita aquele
  contexto; sem contexto selecionado, edita o projeto como hoje).
- `services/autonomo/pipeline.py::carregar_contexto` (nome de variável não relacionado — já existe
  uma dataclass `Contexto` ali, só coincidência de nome) **não muda nesta tarefa**: o modo autônomo
  continua resolvendo só padrão+projeto (sem contexto de usuário), já que ninguém escolhe contexto
  numa pasta monitorada sem tela. **Decisão tomada na implementação**: deixar assim por ora — se um
  dia for preciso, um contexto fixo por pasta/projeto pode ser configurado em `autonomo_config` numa
  tarefa futura, sem mudança no desenho de dados aqui.
- **Decisão tomada na implementação (redução de escopo deliberada)**: `/historico` e `/reverter` não
  ganharam suporte a contexto nesta rodada — editar um contexto na gaveta desliga (`disabled`) os
  botões "Restaurar semente"/"Histórico" com uma explicação no texto de status, em vez de arriscar
  reverter a camada errada por engano. Histórico/reversão por contexto ficam para uma tarefa futura,
  se vierem a ser pedidos.

### 4. Frontend

- Novo seletor dentro de `#resumo-rede-painel`: pill no mesmo estilo visual do `#select-projeto`
  (label "Contexto:" + `<select>` + botão "+ Novo" admin-only), com opção "Nenhum" (= comportamento
  de hoje) sempre primeiro.
- `GET /api/validacao/ajustes/contextos?projeto_codigo=X` alimenta o `<select>` sempre que o
  projeto muda (reaproveita o `onchange` de `#select-projeto`, que já recarrega outras regras).
- `localStorage['contexto_selecionado_<codigo_do_projeto>']` — escopado por projeto (um contexto de
  um projeto não existe em outro).
- Nova função irmã de `codigoDoProjetoSelecionado()`: `contextoSelecionado()`.
- Botão **Ajustar** (e os demais pontos que chamam `/api/validacao/ajustes*`) passam a enviar
  `contexto: contextoSelecionado() || null` junto com `projeto_codigo`.
- A aba/gaveta de edição de Ajustes (`static/painel_ajustes.js`) passa a mostrar, quando um
  contexto está selecionado, um aviso "Editando o contexto '34,5kV'" e opera sobre o overlay do
  contexto em vez do overlay do projeto — reaproveitando a MESMA UI de ligar/desligar/sobrescrever
  que já existe, só mudando o alvo da leitura/escrita.
- Trocar de contexto **não** chama `atualizarResumoRedeUI()` nem reaplica nada — só grava a
  seleção, conforme decisão do usuário.

## Critérios de aceite

- [x] Criar um contexto novo num projeto (`POST .../contextos`) e ligar/desligar ajustes dentro dele
  não afeta os ajustes efetivos do projeto quando nenhum contexto está selecionado.
- [x] Selecionar um contexto e rodar "Ajustar" usa a lista de ajustes daquele contexto (ligados no
  projeto E ligados no contexto — ou religados pelo contexto, se o contexto sobrescrever `ativa`).
- [x] Dois contextos do mesmo projeto podem ter conjuntos de ajustes completamente diferentes entre
  si, sem um afetar o outro.
- [x] Excluir um contexto não afeta os ajustes do projeto nem de outros contextos.
- [x] Sem contexto selecionado, toda rota de `/api/validacao/ajustes*` devolve exatamente o mesmo
  resultado de antes desta tarefa (teste de regressão byte a byte, não só "sem erro").
- [x] Seletor de contexto aparece na linha de totais, lista os contextos do projeto selecionado,
  persiste a escolha por projeto, e some/reseta corretamente ao trocar de projeto.
- [x] Documentação `.ai` atualizada conforme `RULES.md` Regra 9
- [x] `STATE.md` atualizado conforme `RULES.md` Regra 10

## Riscos

- **Maior risco**: alguma rota de Ajustes passar a exigir `contexto` por engano (quebrando quem não
  usa a funcionalidade) — mitigado pelo critério de aceite de regressão byte a byte.
- UI do `painel_ajustes.js` precisa deixar claríssimo **qual camada está sendo editada** (projeto
  vs. contexto) — confundir as duas levaria o usuário a editar o projeto pensando que está editando
  só o contexto, ou vice-versa.
- Perda do `origem` detalhado entre as duas camadas (ver limitação aceita na seção 2) — se um dia
  isso incomodar na prática, exige estender `efetivo()` para aceitar uma origem "herdada" em vez de
  recalcular do zero.
