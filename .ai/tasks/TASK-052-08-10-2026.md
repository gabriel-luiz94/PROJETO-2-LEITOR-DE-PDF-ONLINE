# TASK-052-08-10-2026

**Tabela base de orçamento: visualização e edição escopadas por projeto**

> Pedido do usuário: "Da forma como esta estruturada eu posso colocar uma regra de um projeto
> estando dentro de outro. Quero que seja exibida por projeto. Se eu estiver com o projeto Paraíba
> por exemplo. A visualização e edição da tabela alterará apenas as regras do projeto Paraíba.
> Poderia analisar e montar uma estratégia pra mim? Sem perda de dados e com o mínimo de alteração
> no supabase." Pedido de **análise e desenho de estratégia**, não de implementação — aguardando
> autorização. Decisões já confirmadas pelo usuário (via perguntas diretas, 2026-10-08):
> (1) linhas sem projeto (genéricas) ficam fora da visão por projeto, num filtro/aba separado; (2)
> o campo Projeto de cada linha passa a ser travado no projeto selecionado na tela, não texto livre
> (com uma ressalva pras linhas compartilhadas entre projetos — ver item 4.1); (3) as ações em massa
> (Importar CSV Master, Sincronizar Tudo) passam a agir só sobre o projeto selecionado por padrão,
> com um modo "todos os projetos" separado e com aviso reforçado; (4) linhas compartilhadas entre
> projetos específicos (`"PARAIBA/PARAIBANOVO"`) aparecem na visão de cada um dos projetos que elas
> tocam, mas protegidas de edição/exclusão em massa (ver item 4.1).
>
> **Análise feita sobre o dado real** (CSV exportado do Supabase pelo usuário, 2.646 linhas da
> `tabela_orcamento_master` de produção — não um ambiente de teste): ver números na seção Contexto.
> O banco local deste sandbox (SQLite vazio, sem Supabase configurado) **não** reflete a produção —
> foi descartado como fonte depois que o usuário confirmou que o real tem também o projeto
> PARAIBANOVO, que não existia no banco local.

## Objetivo

Reestruturar a tela `/orcamento` (Base de Orçamento) para que a visualização e a edição sejam
escopadas pelo projeto selecionado — igual ao padrão já usado em `/resumo` (`#select-projeto`) —
sem alterar o contrato de dados que o motor de cálculo já usa, sem perda de dados, e com o mínimo
de alteração estrutural no Supabase (idealmente nenhuma).

## Contexto

### O que já existe e não muda

- `tabela_orcamento` (edições locais do usuário, só SQLite, não sincroniza com Supabase) e
  `tabela_orcamento_master` (tabela oficial do admin, SQLite **e** Supabase) **já têm a coluna
  `projeto`** (`database.py:395,430`; `scripts/schema_supabase.sql:45`). Não é um problema de
  schema — é de UI e de lógica de salvamento. **Nenhuma coluna nova é necessária.**
- `services/orcamento_calc.py:processar_calculo` (RN-06, `CONTEXT.md §7`) já trata `projeto` com a
  cascata correta: linha com `projeto` vazio é genérica (vale pra qualquer projeto); linha com
  `projeto` preenchido só entra no match se bater com o projeto do cálculo (`:102-155`, comparação
  por `.strip().upper()`). **Esse contrato não pode mudar** — o motor de cálculo precisa continuar
  recebendo a base inteira (todos os projetos + genéricas) e filtrando no match, não uma base já
  pré-filtrada por fora.
- **Achado central desta análise, confirmado no dado real (ver abaixo): `projeto` não é um valor
  único.** `processar_calculo:121,158` faz `row_proj.split("/")` — uma linha pode pertencer a
  **vários projetos ao mesmo tempo** (ex.: `"PARAIBA/PARAIBANOVO"` significa "vale pra PARAIBA OU
  PARAIBANOVO"). Isso já é usado de verdade hoje, não é um caso hipotético (108 linhas na produção).
  Qualquer filtro por projeto nesta tarefa — na tela e nas ações em massa — precisa testar
  **pertencimento** a essa lista (`projeto_selecionado in row_proj.split("/")`), nunca igualdade de
  string. Reaproveitar a mesma lógica do motor de cálculo (extrair um helper comum), não reescrever
  essa regra uma terceira vez (já é regra de negócio duplicada entre `orcamento_calc.py` e, em
  algum grau, `static/resumo.js` — não adicionar um quarto lugar).
- `GET /api/orcamento/dados` (`routers/orcamento.py:81`) é usado em dois lugares com necessidades
  diferentes: (1) `static/orcamento.html` (tela de edição, hoje sem filtro — mostra tudo); (2)
  `static/resumo.js` (`syncTotalizadora`, carrega a base pra calcular a Totalizadora/orçamento) —
  **esse segundo uso precisa continuar recebendo a base completa**, sem filtro, porque é o que
  alimenta `processar_calculo`.
- `get_merged_orcamento()` (`services/sync_service.py:76`): se o usuário tem qualquer linha em
  `tabela_orcamento`, usa **todas** as linhas dele (de todos os projetos) no lugar da master; senão,
  usa a master inteira; senão, o seed. Não há merge por linha — é "qual tabela inteira usar".

### O problema de hoje (confirmado no código, não só relatado)

- `static/orcamento.html` carrega **tudo de uma vez** (`carregarDados()` chama `/api/orcamento/dados`
  sem nenhum filtro) numa única tabela editável, com a coluna PROJETO como texto livre por linha. O
  filtro de coluna (`filterTable()`) é **só visual** — esconde `<tr>` com `display:none`, mas não
  remove do DOM; ações de salvar/sincronizar (`salvarAlteracoes()`, `sincronizarTudoNuvem()`) usam
  `tbody.querySelectorAll("tr")`, que pega **as linhas escondidas também**. Ou seja: hoje não existe
  nenhum escopo real — é só uma tabela gigante com todos os projetos misturados, e o usuário
  confia na própria disciplina pra não digitar/apagar a linha errada.
- **Risco de perda de dados já existente, mais grave do que o relatado** (achado durante esta
  análise, fora do que foi pedido, registrado aqui porque a nova estratégia PRECISA resolvê-lo
  também, senão fica pior): `POST /api/admin/upload-master` (`routers/admin.py:369-447`) e
  `POST /api/admin/sync-master-all` (`routers/admin.py:449-517`) fazem
  `DELETE FROM tabela_orcamento_master` (**sem filtro, todos os projetos**) local **e** no Supabase
  (`supabase.table(...).delete().neq("id", 0)`) antes de reinserir só o que veio no CSV/payload.
  Hoje isso "funciona" só porque a tela sempre carrega e reenvia a tabela inteira. Se a edição
  passar a ser por projeto sem mudar esse DELETE, importar um CSV só de Paraíba **apagaria Rondônia
  inteira**, local e na nuvem, pra todo mundo.

## Comportamento desejado

### 1. Seletor de projeto na tela `/orcamento`

Reaproveitar o padrão de `/resumo` (`#select-projeto`, populado por `GET /api/projetos`,
`localStorage['projeto_selecionado']`) — mesma chave de `localStorage`, pra manter o projeto
selecionado consistente entre as telas quando o usuário navega de uma pra outra.

- Sem projeto selecionado: tela mostra um estado vazio pedindo pra escolher um projeto (não mostra
  "tudo" por padrão — isso seria voltar ao problema atual).
- Com projeto selecionado (ex.: PARAIBA): tabela mostra as linhas de
  `tabela_orcamento_master`/`tabela_orcamento` cujo `projeto` (normalizado por `.strip().upper()`,
  dividido por `/`) **contém** o projeto selecionado — igual ao que `processar_calculo` já faz.
  Isso inclui tanto as exclusivas (`projeto = "PARAIBA"`) quanto as compartilhadas
  (`projeto = "PARAIBA/PARAIBANOVO"`) — ver seção 5 para como essas são tratadas na tela.
- Linhas com `projeto` vazio (genéricas) **não aparecem** na visão por projeto — ficam num filtro/
  aba separado explícito, ex. "Comuns a todos os projetos" (decisão confirmada: aba/filtro
  separado, não misturadas por padrão).
- Uma aba/filtro adicional "Projeto não reconhecido" mostra linhas cujo `projeto` não é vazio nem
  bate com nenhum projeto cadastrado em `GET /api/projetos` — proteção pra que uma linha com typo
  no nome do projeto não fique invisível pra sempre atrás do filtro novo (ver Riscos).

### 2. Campo Projeto travado (decisão confirmada, com ressalva pras compartilhadas)

- Dentro do contexto de um projeto selecionado, "+ Adicionar Linha"/"+ Nova Linha Master" criam a
  linha já com `projeto` = projeto selecionado (valor único), **sem campo de texto livre** para
  esse valor (campo somente leitura, ou removido da grade — mostrado como rótulo fixo acima da
  tabela: "Editando: PARAIBA"). Isso cobre o caso comum (linha nova pertence a um projeto só).
- Mover uma linha exclusiva de um projeto pra outro, ou transformar uma exclusiva em compartilhada,
  passa a ser uma ação explícita e deliberada — não faz parte deste desenho inicial (fora de
  escopo; se precisar, fica pra uma tarefa futura).
- Na aba "Comuns a todos os projetos", o campo Projeto continua vazio/fixo (não editável como
  texto livre também, pra não reintroduzir o problema ali).
- **Linhas compartilhadas (`projeto` com `/`) nunca ficam com o campo travado num valor único** —
  ver seção 5, que trata esse caso separadamente porque "travar num valor só" destruiria o
  compartilhamento.

### 3. Backend: novo parâmetro `projeto`, aditivo (não quebra o uso existente)

- `GET /api/orcamento/dados` ganha um parâmetro de query **opcional** `projeto: str | None`. Sem
  ele (comportamento atual, usado por `resumo.js`/`syncTotalizadora`): devolve a base inteira,
  sem mudança. Com ele: filtra as linhas por **pertencimento** — `projeto` vazio (genérica) **ou**
  o projeto selecionado presente na lista `projeto.split("/")` (cobre exclusivas e compartilhadas)
  — mesma regra do cálculo, extraída uma única vez num helper comum (ex.:
  `services/orcamento_calc.py::projeto_bate(row_projeto, projeto_selecionado)`, hoje duplicada
  inline duas vezes dentro do próprio `processar_calculo`) e reaproveitada aqui, em vez de escrever
  essa comparação uma quarta vez.
  - Dúvida de design a decidir na implementação: a tela deve usar esse mesmo endpoint com
    `?projeto=X` (reaproveita tudo) ou um endpoint dedicado `GET /api/admin/orcamento-master?projeto=X`
    só para a tela de edição (mais explícito sobre "isto é visão de admin", não entra na
    cascata de merge usuário/master/seed)? Recomendo o endpoint dedicado — a tela de edição do
    admin deveria ver **a master diretamente** (`tabela_orcamento_master`), não o resultado já
    mesclado com as edições de um usuário específico (`get_merged_orcamento`), que é um conceito
    de runtime do cálculo, não de administração da base.
- `POST /api/orcamento/salvar` e `POST /api/admin/add-row`: sem mudança de contrato (já são por
  linha/aditivos) — a UI é que passa a mandar sempre o `projeto` travado.
- `POST /api/admin/upload-master` e `POST /api/admin/sync-master-all`: ganham um parâmetro
  `projeto` (form field / body). Com ele, o `DELETE` é escopado por **igualdade exata** (não por
  pertencimento) — `DELETE FROM tabela_orcamento_master WHERE UPPER(TRIM(projeto)) =
  UPPER(TRIM(:projeto))` (local **e** Supabase, `.eq("projeto", projeto_normalizado)` em vez de
  `.neq("id", 0)`) — de propósito mais estreito que o `GET` acima: isso garante que o DELETE nunca
  atinge uma linha compartilhada (`"PARAIBA/PARAIBANOVO"` não é igual a `"PARAIBA"`) nem uma
  genérica (vazio não é igual a `"PARAIBA"`). Só as linhas do CSV/payload com `projeto` igual ao
  selecionado são aceitas/inseridas; linha com `projeto` diferente é rejeitada com erro claro.
  Sem o parâmetro (modo "todos os projetos", decisão confirmada que continua existindo): comportamento
  atual, inalterado, mas movido pra uma ação separada e com confirmação textual mais forte
  (já existe um `confirm()` em `sincronizarTudoNuvem()` — reforçar o texto pra deixar claro que
  afeta TODOS os projetos, não só o que está na tela).
- Nenhuma mudança em `tabela_orcamento_master`/`tabela_orcamento` (SQLite) nem no Supabase —
  **zero `ALTER TABLE`, zero coluna nova.**

### 4. Linhas "Comuns a todos os projetos" (genéricas)

- Aba/filtro separado na mesma tela (decisão confirmada), explicitamente rotulado, para reduzir o
  risco de editar/apagar por engano uma linha que afeta múltiplos projetos pensando que é só do
  projeto atual.
- As ações em massa escopadas por projeto (seção 3) **nunca tocam** linhas com `projeto` vazio —
  o filtro do DELETE é `projeto = :selecionado`, não `projeto = :selecionado OR projeto = ''`.
  Editar as genéricas é uma ação separada, só disponível nessa aba.

### 5. Linhas compartilhadas entre projetos específicos (decisão confirmada)

As 108 linhas hoje com `projeto = "PARAIBA/PARAIBANOVO"` (ou qualquer combinação futura de 2+
projetos) exigem tratamento diferente tanto das exclusivas (seção 2) quanto das genéricas (seção
4), porque "travar o campo no projeto selecionado" apagaria silenciosamente o outro projeto da
lista — exatamente o tipo de perda de dados que esta tarefa existe pra evitar.

- **Aparecem na visão de cada projeto que tocam** (ex.: aparecem tanto vendo PARAIBA quanto vendo
  PARAIBANOVO) — nunca ficam escondidas atrás do filtro, pra não arriscar o admin recriar uma linha
  que já existe (duplicação, que polui o cálculo — `processar_calculo` usa **todos** os matches
  exatos de uma chave, então uma duplicata pode somar/contar errado, não só "ficar feio na tela").
- Aparecem com uma etiqueta visual clara, ex. "🔗 Compartilhada com PARAIBANOVO".
- O campo Projeto dessas linhas é **somente leitura** na visão por projeto — mudar a lista de
  projetos que uma linha compartilhada toca é uma ação separada ("Gerenciar projetos desta linha"),
  não um efeito colateral de editar outro campo. Essa ação de gerenciar pode ficar de fora da
  primeira entrega (as linhas continuam visíveis e protegidas sem ela); se ficar de fora, registrar
  como item futuro explícito.
- As ações em massa escopadas por projeto (seção 3) **nunca tocam linhas compartilhadas** — o
  DELETE escopado usa igualdade exata (seção 3), que por construção não bate com um valor contendo
  `/`. Importar um CSV do projeto PARAIBA não apaga nem duplica as 108 linhas
  PARAIBA/PARAIBANOVO; elas são geridas só pela ação separada de "gerenciar projetos desta linha"
  (ou, até essa existir, por uma edição direta no Supabase/CSV de "todos os projetos", fora do
  fluxo escopado).

  `PARAIBANOVO` e a combinação `PARAIBA/PARAIBANOVO`). Não é um problema atual, mas como o campo
  continua existindo como texto livre em pelo menos um fluxo (CSV, Supabase direto), mantenho a aba
  "Projeto não reconhecido" (seção 1) como rede de segurança pra qualquer linha futura que não bata
  nem sozinha nem dentro de uma lista `/` com nenhum projeto cadastrado — pra nunca ficar invisível.
- **Listas `/` com mais de 2 projetos, ou um projeto aparecendo em mais de uma lista diferente** —
  hoje só existe o par PARAIBA/PARAIBANOVO (108 linhas, sempre a mesma combinação), mas o helper de
  pertencimento (seção 3) deve continuar genérico pra N projetos (`split("/")`, sem assumir só 2),
  do jeito que `processar_calculo` já faz.
- **Dois pontos de verdade para "a base" durante a transição**: se a implementação for feita em
  etapas (endpoint novo primeiro, UI depois), garantir que nenhuma etapa intermediária deixe
  `upload-master`/`sync-master-all` escopados **sem** a UI ainda mandar o projeto corretamente —
  isso apagaria a base inteira pensando que ia escopar. Mitigação: implementar e testar o parâmetro
  `projeto` no backend com testes automatizados (`pytest`) ANTES de mudar a UI pra usá-lo, e só
  then trocar o front.
- **Supabase sem transação multi-tabela**: o padrão já existente de "DELETE depois INSERT" (sem
  transação atômica no Supabase, diferente do SQLite que usa `BEGIN/COMMIT`) significa que uma
  falha de rede entre o DELETE e o INSERT pode deixar o projeto selecionado com a master vazia na
  nuvem até a próxima sincronização bem-sucedida. Esse risco já existe hoje (é do padrão atual, não
  introduzido por esta tarefa) — mitigado por ser bem menor em escopo (um projeto, não a base
  inteira) depois desta mudança.
