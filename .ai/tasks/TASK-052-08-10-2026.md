## Objetivo

Reestruturar a tela `/orcamento` (Base de Orçamento) para que a visualização e a edição sejam
**totalmente separadas por projeto** — cada projeto com sua própria fatia da base técnica,
importável/editável/excluível independentemente — igual ao padrão já usado em `/resumo`
(`#select-projeto`), sem alterar o contrato de dados que o motor de cálculo já usa, sem perda de
dados, e com o mínimo de alteração estrutural no Supabase (nenhuma — a migração de dados da seção
5 não é uma mudança de schema).

## Contexto

### O que já existe e não muda

- `tabela_orcamento` (edições locais do usuário, só SQLite, não sincroniza com Supabase) e
  `tabela_orcamento_master` (tabela oficial do admin, SQLite **e** Supabase) **já têm a coluna
  `projeto`** (`database.py:395,430`; `scripts/schema_supabase.sql:45`). Não é um problema de
  schema — é de UI e de lógica de salvamento. **Nenhuma coluna nova é necessária.**
- `services/orcamento_calc.py:processar_calculo` (RN-06, `CONTEXT.md §7`) já trata `projeto` com a
  cascata correta: linha com `projeto` vazio é genérica (vale pra qualquer projeto); linha com
  `projeto` preenchido só entra no match se bater com o projeto do cálculo (`:102-155`, comparação
  por `.strip().upper()`). **Esse contrato não pode mudar** — o motor de cálculo precisa continuar
  recebendo a base inteira (todos os projetos + genéricas) e filtrando no match, não uma base já
  pré-filtrada por fora.
- **Achado central desta análise, confirmado no dado real: `projeto` hoje pode valer mais de um
  projeto ao mesmo tempo.** `processar_calculo:121,158` faz `row_proj.split("/")` — uma linha pode
  pertencer a vários projetos (ex.: `"PARAIBA/PARAIBANOVO"` = "vale pra PARAIBA OU PARAIBANOVO").
  Isso é usado de verdade hoje (108 linhas na produção). **Essa capacidade do motor de cálculo não
  é removida** — continua lendo `/` normalmente, por robustez (alguém pode editar direto no
  Supabase e recriar esse padrão). Mas a **migração desta tarefa (seção 5) elimina os usos
  existentes dele**, e a tela nova nunca mais produz um valor com `/`.
- `GET /api/orcamento/dados` (`routers/orcamento.py:81`) é usado em dois lugares com necessidades
  diferentes: (1) `static/orcamento.html` (tela de edição, hoje sem filtro — mostra tudo); (2)
  `static/resumo.js` (`syncTotalizadora`, carrega a base pra calcular a Totalizadora/orçamento) —
  **esse segundo uso precisa continuar recebendo a base completa**, sem filtro, porque é o que
  alimenta `processar_calculo`.
- `get_merged_orcamento()` (`services/sync_service.py:76`): se o usuário tem qualquer linha em
  `tabela_orcamento`, usa **todas** as linhas dele (de todos os projetos) no lugar da master; senão,
  usa a master inteira; senão, o seed. Não há merge por linha — é "qual tabela inteira usar".

### O problema de hoje (confirmado no código, não só relatado)

- `static/orcamento.html` carrega **tudo de uma vez** (`carregarDados()` chama `/api/orcamento/dados`
  sem nenhum filtro) numa única tabela editável, com a coluna PROJETO como texto livre por linha. O
  filtro de coluna (`filterTable()`) é **só visual** — esconde `<tr>` com `display:none`, mas não
  remove do DOM; ações de salvar/sincronizar (`salvarAlteracoes()`, `sincronizarTudoNuvem()`) usam
  `tbody.querySelectorAll("tr")`, que pega **as linhas escondidas também**. Ou seja: hoje não existe
  nenhum escopo real — é só uma tabela gigante com todos os projetos misturados, e o usuário
  confia na própria disciplina pra não digitar/apagar a linha errada.
- **Risco de perda de dados já existente, mais grave do que o relatado** (achado durante esta
  análise, fora do que foi pedido, registrado aqui porque a nova estratégia PRECISA resolvê-lo
  também, senão fica pior): `POST /api/admin/upload-master` (`routers/admin.py:369-447`) e
  `POST /api/admin/sync-master-all` (`routers/admin.py:449-517`) fazem
  `DELETE FROM tabela_orcamento_master` (**sem filtro, todos os projetos**) local **e** no Supabase
  (`supabase.table(...).delete().neq("id", 0)`) antes de reinserir só o que veio no CSV/payload.
  Hoje isso "funciona" só porque a tela sempre carrega e reenvia a tabela inteira. Se a edição
  passar a ser por projeto sem mudar esse DELETE, importar um CSV só de Paraíba **apagaria Rondônia
  inteira**, local e na nuvem, pra todo mundo.

## Comportamento desejado

### 1. Seletor de projeto na tela `/orcamento`

Reaproveitar o padrão de `/resumo` (`#select-projeto`, populado por `GET /api/projetos`,
`localStorage['projeto_selecionado']`) — mesma chave de `localStorage`, pra manter o projeto
selecionado consistente entre as telas quando o usuário navega de uma pra outra.

- Sem projeto selecionado: tela mostra um estado vazio pedindo pra escolher um projeto (não mostra
  "tudo" por padrão — isso seria voltar ao problema atual).
- Com projeto selecionado (ex.: PARAIBA): tabela mostra **só** as linhas de
  `tabela_orcamento_master`/`tabela_orcamento` cujo `projeto` (normalizado por `.strip().upper()`)
  é **exatamente igual** ao projeto selecionado — depois da migração da seção 5, toda linha
  nomeada é exclusiva de um projeto só, então igualdade simples basta (não precisa mais testar
  pertencimento numa lista `/` pra decidir o que a tela mostra).
- Linhas com `projeto` vazio (genéricas) **não aparecem** na visão por projeto — ficam num filtro/
  aba separado explícito, ex. "Comuns a todos os projetos" (decisão confirmada: aba/filtro
  separado, não misturadas por padrão, fora do escopo de edição por projeto desta tarefa).
- Uma aba/filtro adicional "Projeto não reconhecido" mostra linhas cujo `projeto` não é vazio nem
  bate com nenhum projeto cadastrado em `GET /api/projetos` — proteção pra que uma linha com typo
  no nome do projeto (ou um `/` que volte a aparecer por edição manual futura) não fique invisível
  pra sempre atrás do filtro novo (ver Riscos).

### 2. Campo Projeto travado (decisão confirmada)

- Dentro do contexto de um projeto selecionado, "+ Adicionar Linha"/"+ Nova Linha Master" criam a
  linha já com `projeto` = projeto selecionado, **sem campo de texto livre** para esse valor (campo
  somente leitura, ou removido da grade — mostrado como rótulo fixo acima da tabela: "Editando:
  PARAIBA").
- Toda linha nomeada (depois da migração da seção 5) é exclusiva de um projeto só — **não existe
  mais nenhuma linha compartilhada pra tratar como caso especial**. Editar, excluir ou substituir
  (via CSV) uma linha dentro do contexto de um projeto nunca tem efeito em nenhum outro.
- Mover uma linha de um projeto pra outro continua sendo uma ação explícita e deliberada — fora de
  escopo desta tarefa (se precisar, fica pra uma tarefa futura).
- Na aba "Comuns a todos os projetos", o campo Projeto continua vazio/fixo (não editável como
  texto livre também, pra não reintroduzir o problema ali) — essas linhas continuam fora do escopo
  de edição por projeto (decisão confirmada).

### 3. Backend: novo parâmetro `projeto`, aditivo (não quebra o uso existente)

- `GET /api/orcamento/dados` ganha um parâmetro de query **opcional** `projeto: str | None`. Sem
  ele (comportamento atual, usado por `resumo.js`/`syncTotalizadora`): devolve a base inteira,
  sem mudança. Com ele: filtra as linhas por `UPPER(TRIM(projeto)) = UPPER(TRIM(:projeto))` —
  igualdade simples, não pertencimento (depois da migração da seção 5, nenhuma linha nomeada tem
  `/` no valor).
  - Dúvida de design a decidir na implementação: a tela deve usar esse mesmo endpoint com
    `?projeto=X` (reaproveita tudo) ou um endpoint dedicado `GET /api/admin/orcamento-master?projeto=X`
    só para a tela de edição (mais explícito sobre "isto é visão de admin", não entra na
    cascata de merge usuário/master/seed)? Recomendo o endpoint dedicado — a tela de edição do
    admin deveria ver **a master diretamente** (`tabela_orcamento_master`), não o resultado já
    mesclado com as edições de um usuário específico (`get_merged_orcamento`), que é um conceito
    de runtime do cálculo, não de administração da base.
- `POST /api/orcamento/salvar` e `POST /api/admin/add-row`: sem mudança de contrato (já são por
  linha/aditivos) — a UI é que passa a mandar sempre o `projeto` travado.
- `POST /api/admin/upload-master` e `POST /api/admin/sync-master-all`: ganham um parâmetro
  `projeto` (form field / body). Com ele: o `DELETE` passa a ser
  `DELETE FROM tabela_orcamento_master WHERE UPPER(TRIM(projeto)) = UPPER(TRIM(:projeto))` (local
  **e** Supabase, `.eq("projeto", projeto_normalizado)` em vez de `.neq("id", 0)`), e só as linhas
  do CSV/payload com `projeto` igual ao selecionado são aceitas/inseridas (linha com `projeto`
  diferente do selecionado é rejeitada com erro claro, não silenciosamente ignorada). Isso cobre
  exatamente o pedido "importar uma planilha em cada projeto de forma separada": o DELETE nunca
  mais atinge outro projeto, porque é igualdade exata sobre um valor que (depois da migração) é
  sempre um nome só.
  Sem o parâmetro (modo "todos os projetos", decisão confirmada que continua existindo):
  comportamento atual, inalterado, mas movido pra uma ação separada e com confirmação textual mais
  forte (já existe um `confirm()` em `sincronizarTudoNuvem()` — reforçar o texto pra deixar claro
  que afeta TODOS os projetos, não só o que está na tela).
- Nenhuma mudança em `tabela_orcamento_master`/`tabela_orcamento` (SQLite) nem no Supabase —
  **zero `ALTER TABLE`, zero coluna nova.**

### 4. Linhas "Comuns a todos os projetos" (genéricas) — fora do escopo de separação

- Aba/filtro separado na mesma tela (decisão confirmada), explicitamente rotulado, para reduzir o
  risco de editar/apagar por engano uma linha que afeta todos os projetos pensando que é só do
  projeto atual.
- As ações em massa escopadas por projeto (seção 3) **nunca tocam** linhas com `projeto` vazio —
  o filtro do DELETE é `projeto = :selecionado`, não `projeto = :selecionado OR projeto = ''`.
  Editar as genéricas é uma ação separada, só disponível nessa aba — decisão confirmada: essa
  categoria **não** faz parte do pedido de "projetos totalmente manipuláveis de forma separada"
  (ela existe justamente pra ser compartilhada por todos, de propósito).

### 5. Migração única: linhas compartilhadas entre projetos nomeados → exclusivas independentes (decisão confirmada)

Resolve a tensão entre os dois pedidos do usuário: "sem perda de dados" e "editando inclusive as
linhas compartilhadas". Travar o campo Projeto (seção 2) e escopar o DELETE por igualdade exata
(seção 3) só funcionam de forma segura se **nenhuma linha tiver mais de um projeto no valor** —
por isso a migração acontece antes (ou no mesmo deploy) de ligar a tela nova.

- **O que a migração faz**, uma única vez, sobre as 108 linhas hoje com `projeto` contendo `/`
  (ex.: `"PARAIBA/PARAIBANOVO"`): pra cada uma, divide a lista de projetos (`split("/")`) e cria
  **uma linha exclusiva por projeto da lista**, cada cópia com os mesmos valores de
  `ativo/desc_ativo/componente/mdo/codigo/desc_codigo/fator_i/fator_r/filtro/origem` que a linha
  original tinha — só o `projeto` muda, de "A/B" para "A" numa cópia e "B" na outra. A linha
  original é então apagada (ou atualizada para uma das cópias, reaproveitando o `id`) — sem duplicar
  o conceito, o resultado final tem exatamente 2 linhas onde antes havia 1.
  Pra 108 linhas com 2 projetos cada: **+108 linhas novas**, nenhuma removida em valor (108 ficam
  com o `id` antigo reaproveitado + `projeto` reduzido a 1 nome, 108 são inseridas do zero) — total
  2.646 → 2.754.
- **Roda local e no Supabase**, no mesmo padrão aditivo que `add_master_row` já usa (não é
  `ALTER TABLE`, é dado) — nenhuma coluna nova, nenhuma mudança de schema.
- **Idempotente**: rodar a migração duas vezes não deve duplicar de novo — a implementação verifica,
  antes de migrar, se já não sobra nenhuma linha com `/` no campo `projeto` (condição de parada
  natural: se `WHERE projeto LIKE '%/%'` não retorna nada, não há o que migrar).
- **Depois da migração, o conceito "linha compartilhada" deixa de existir** na `tabela_orcamento_master`
  mantida pela tela nova — cada linha nomeada pertence a exatamente um projeto, 100% editável,
  excluível e substituível por CSV dentro do contexto desse projeto, sem nenhum caso especial no
  código da tela nem das rotas (seções 1 a 3 não precisam de lógica extra pra esse caso).
- `processar_calculo` continua aceitando `/` no campo `projeto` (seção "O que já existe e não
  muda") — não removido do motor de cálculo, só deixa de ser produzido pela tela nova. Se alguém
  editar direto no Supabase e recriar esse padrão no futuro, o cálculo continua funcionando, mas a
  tela por projeto trataria essa linha como "Projeto não reconhecido" (seção 1) — comportamento
  aceitável, já que seria uma edição fora do fluxo normal.
- Expor a migração como uma ação explícita de admin (endpoint/botão "Migrar linhas compartilhadas",
  executado uma vez, com um resumo do que vai mudar antes de confirmar) — não uma migração
  automática e silenciosa no primeiro carregamento da tela nova, pra manter visibilidade sobre a
  única escrita em massa que esta tarefa faz nos dados reais.

## Exemplos

### Entrada

1. Antes da migração: base master real tem 1.018 linhas RONDONIA, 108 PARAIBA, 101 PARAIBANOVO,
   108 PARAIBA/PARAIBANOVO, 1.311 genéricas. Migração roda.
2. Depois da migração, admin seleciona PARAIBA em `/orcamento` e importa um CSV com 12 linhas,
   todas PARAIBA — inclusive substituindo o valor de um ativo que antes era uma das 108
   compartilhadas.
3. Admin abre a visão de PARAIBANOVO (sem importar nada) depois da ação acima.

### Resultado esperado

1. Depois da migração: 1.018 RONDONIA + 216 PARAIBA + 209 PARAIBANOVO + 1.311 genéricas = 2.754
   linhas. Nenhum valor mudou, só a contagem por categoria nomeada.
2. Depois da importação: as 216 linhas PARAIBA são substituídas pelas 12 novas (incluindo a que
   era compartilhada). As 1.018 RONDONIA, as 209 PARAIBANOVO e as 1.311 genéricas continuam
   exatamente como estavam, local e Supabase.
3. A visão de PARAIBANOVO mostra as 209 linhas exclusivas dela, **inalteradas** — inclusive a cópia
   do ativo que, em PARAIBA, acabou de ser substituída pelo CSV. A importação do passo 2 não afetou
   nada que apareça aqui.

## Riscos

- **Typos/inconsistência de grafia no campo `projeto`** — checado contra o CSV real de produção
  (2.646 linhas): **nenhuma variante encontrada hoje** (só `''`, `RONDONIA`, `PARAIBA`,
  `PARAIBANOVO` e a combinação `PARAIBA/PARAIBANOVO`). Não é um problema atual, mas como o campo
  continua existindo como texto livre em pelo menos um fluxo (CSV, Supabase direto), mantenho a aba
  "Projeto não reconhecido" (seção 1) como rede de segurança — pra nunca ficar invisível, inclusive
  se um `/` voltar a aparecer por edição manual futura (fora do fluxo normal da tela).
- **Migração é uma escrita real nos dados de produção** (108 → 216 linhas, local e Supabase) — não
  reversível automaticamente (embora não destrutiva: nada é perdido, só duplicado/dividido).
  Mitigação: expor como ação explícita de admin (seção 5), não automática; logar antes/depois
  (quantas linhas tinham `/`, quantas foram criadas); testar primeiro contra uma cópia/exportação,
  não direto em produção sem conferir.
- **Ordem de implementação**: a migração (seção 5) precisa rodar **antes** de ligar o DELETE
  escopado por igualdade exata (seção 3) pra valer — se o DELETE escopado for ativado antes da
  migração, uma linha ainda compartilhada (`"PARAIBA/PARAIBANOVO"`) nunca seria alcançada por
  nenhum DELETE de projeto único (o que é seguro, só "trava" ela intocável até a migração rodar) —
  não é destrutivo, mas pode confundir se a ordem não for seguida e comunicada.
- **Dois pontos de verdade para "a base" durante a transição**: se a implementação for feita em
  etapas (migração → endpoint novo → UI), garantir que nenhuma etapa intermediária deixe
  `upload-master`/`sync-master-all` escopados **sem** a UI ainda mandar o projeto corretamente —
  isso apagaria a base inteira pensando que ia escopar. Mitigação: implementar e testar o parâmetro
  `projeto` no backend com testes automatizados (`pytest`) ANTES de mudar a UI pra usá-lo.
- **Supabase sem transação multi-tabela**: o padrão já existente de "DELETE depois INSERT" (sem
  transação atômica no Supabase, diferente do SQLite que usa `BEGIN/COMMIT`) significa que uma
  falha de rede entre o DELETE e o INSERT pode deixar o projeto selecionado com a master vazia na
  nuvem até a próxima sincronização bem-sucedida. Esse risco já existe hoje (é do padrão atual, não
  introduzido por esta tarefa) — mitigado por ser bem menor em escopo (um projeto, não a base
  inteira) depois desta mudança.

## Decisões tomadas durante a implementação

- Seção 3 deixava aberta a escolha entre reaproveitar `GET /api/orcamento/dados?projeto=` ou criar
  um endpoint dedicado de admin. Implementado reaproveitando o endpoint existente (parâmetros
  opcionais `projeto`/`genericas`/`nao_reconhecido`, filtrando em Python depois de
  `get_merged_orcamento`) — menos código novo, e como a maioria das contas não tem edições
  pessoais salvas (`tabela_orcamento` com `user_id`), o resultado na prática reflete a master
  diretamente na grande maioria dos casos. Sem endpoint novo de admin.
- Achado durante a implementação, fora do previsto na seção 3: `POST /api/orcamento/salvar`
  (cópia pessoal do usuário em `tabela_orcamento`) também fazia `DELETE` sem filtro de projeto
  (só por `user_id`) — o mesmo risco das ações em massa da master, só que na tabela pessoal.
  Corrigido no mesmo padrão (parâmetro `projeto` opcional em `SalvarOrcamentoRequest`, DELETE
  escopado quando presente); a tela só chama `salvarAlteracoes()` com a aba "Projeto selecionado"
  ativa e um projeto escolhido, exatamente pra nunca cair no caso sem escopo.
- A normalização usada por `processar_calculo` (`.strip().upper()`) foi extraída pra
  `services/sync_service.py::normalizar_projeto`/`validar_linhas_do_projeto`/
  `filtrar_linhas_por_categoria`, reaproveitadas por `routers/orcamento.py` e `routers/admin.py` —
  nenhuma duplicação nova da regra de comparação de projeto.
