# TASK-040-05-10-2026

**Ligar o monitor de conectividade (ping periódico + reconexão proativa + indicador online/offline)**

> Parte 2 de 3 do pedido do usuário "garantir que os dados estejam sempre disponíveis", depende da
> TASK-039 (reconexão reativa) já existir — reaproveita o mesmo `reset_supabase_client()`.
> Implementada em 2026-10-05.

## Objetivo

Ativar o monitor de conectividade já escrito (`services/connectivity_monitor.py`), que hoje existe
mas nunca é chamado, para detectar queda/volta da conexão com o Supabase de forma **proativa**
(sem esperar o próximo request do usuário falhar) e reconectar sozinho, além de alimentar o
indicador visual online/offline que já existe no frontend mas nunca recebe eventos.

## Contexto

Achados confirmados no código:

- `services/connectivity_monitor.py` tem `start_connectivity_monitor()` (linha 61) completo: thread
  daemon que testa a conexão a cada 15s (`supabase.table("configuracoes").select(...)`, linha 29) e
  manda evento WebSocket `{"type": "connectivity", "status": "online"|"offline"}` quando o status
  muda. **Nenhum lugar do projeto chama essa função** — confirmado por busca no repositório inteiro.
- A função **só roda se `APP_MODE != "server"`** (linha 63-64: `if APP_MODE == "server": return`) —
  comentário diz "Apenas desktop". Isso precisa ser revisto: se o usuário também roda em modo
  servidor (ex.: Render, mencionado em outras partes do projeto), o monitor nunca ajudaria lá.
- O worker (`_monitor_worker`, linha 20-58) manipula o event loop do `asyncio` a partir de uma
  thread (`asyncio.get_event_loop()`/`new_event_loop()`/`run_until_complete()`, linha 39-56) — é
  exatamente o padrão já catalogado como frágil em `.ai/STATE.md` (item 23), hoje sem efeito
  prático só porque o worker nunca roda.
- Mesmo ligado hoje, o worker **não chama `reset_supabase_client()`** quando detecta a transição
  offline→online — ele só *reporta* o status, não força o cliente singleton a se recriar. Por isso
  esta tarefa depende da TASK-039 (ou reimplementa o reset aqui, se a 039 não for feita primeiro).
- `.ai/STATE.md` ("Em desenvolvimento / escrito mas não conectado"): "O indicador de status
  online/offline no frontend não recebe eventos" — confirma que o frontend já tem *algo* esperando
  esse evento WebSocket, só não chega nunca.

## Situação atual

Monitor existe, nunca roda; indicador do frontend existe, nunca recebe dado.

## Comportamento desejado

1. Chamar `start_connectivity_monitor()` no `@app.on_event("startup")` do `app.py` (mesmo padrão já
   usado pela vigia do modo autônomo, `app.py:256-266`). **Decisão tomada:** removida a restrição
   `if APP_MODE == "server": return` — o monitor agora roda em ambos os modos (desktop e servidor).
   Justificativa: o problema de conexão relatado pelo usuário não é exclusivo do modo desktop, e o
   custo de uma thread com ping a cada 15s é desprezível; manter a restrição deixaria o modo
   servidor sem a mesma proteção.
2. Ao detectar a transição offline→online (`ConnectivityStatus.is_online` muda de `False` para
   `True`), o worker agora chama `reset_supabase_client()` **antes** de reportar "online" —
   garantindo que a reconexão proativa realmente force um cliente novo, não só reporte um status
   que pode estar desatualizado.
3. Corrigido o padrão frágil de `asyncio` do worker: o loop principal é capturado uma única vez em
   `start_connectivity_monitor()` (chamado de dentro do handler de startup síncrono, que já roda na
   thread do loop do uvicorn) e passado para a thread do monitor; o broadcast usa
   `asyncio.run_coroutine_threadsafe(manager.broadcast(mensagem), loop)` em vez de criar/fechar
   loops novos a cada mudança de status.
4. Indicador do frontend criado do zero (não existia antes, ao contrário do que o `STATE.md`
   sugeria) em `static/resumo.html` (`#indicador-conectividade`, oculto por padrão) e
   `static/resumo.js` (IIFE `conectividade()` que abre um WebSocket para `/ws`, escuta
   `{"type": "connectivity", ...}` e alterna a visibilidade/cor do selo).

## Riscos

- Rodar em modo servidor (se confirmado) significa uma thread de ping a cada 15s por processo —
  desprezível, mas precisa ser avaliado se há múltiplas instâncias/workers do servidor rodando
  (cada um teria seu próprio monitor, o que é aceitável, só redundante).
- `asyncio.run_coroutine_threadsafe` exige ter uma referência válida ao loop principal rodando;
  precisa garantir que o startup captura o loop **depois** que o FastAPI/uvicorn já o criou.
