# TASK-078-25-10-2026

**Serviços com e sem linha viva: coluna LV (LV / LM / A) na tabela base de orçamento e filtro no cálculo**

## Status
AGUARDANDO DECISÕES (só planejamento; nada implementado)

## Objetivo
Diferenciar, na tabela base do orçamento, as linhas que valem para **linha viva**, para **linha morta** ou para **ambas**, e fazer o cálculo escolher só as linhas compatíveis com a operação de cada item.

## Pedido (2026-10-25)
- Nova coluna **LV** na tabela de orçamento, com três valores: **LV** (linha viva), **LM** (linha morta) e **A** (ambos).
- Linha viva é indicada pelo `*` antes da operação: `*I` = instalar em linha viva, `*R`, `*M` etc.
- Comportamento no cálculo:
  - linha da base com **LV** → só é contabilizada para itens de operação **com `*`**;
  - linha da base com **LM** → só é contabilizada para operações **sem `*`**;
  - linha da base com **A** → contabilizada nos **dois** casos.
- Tabelas existentes (sem a coluna): **todas as linhas ficam com `A`** (nada muda no resultado de hoje).

## Situação atual (o que li no código)
- `services/orcamento_calc.py::processar_calculo` já recebe a operação de cada item (`I`, `*I`, `R`, `*R`, `M`, `*M`), mas **o `*` é ignorado na escolha das linhas**: só serve em `is_inst = operacao in ("I", "*I")` (soma I × soma R). Hoje `*I` e `I` produzem o mesmo resultado.
- A escolha das linhas passa por um único filtro, `_matches_origem(row)` (coluna `origem`, TASK anterior), usado nos 5 passos da cascata: ativo → componente → desc_ativo exato → desc_ativo parcial → código direto; e de novo ao expandir **todos os códigos do componente**. É o ponto natural para o novo filtro de LV.
- A coluna `origem` foi adicionada em: `database.py` (CREATE + ALTER nas duas tabelas), `scripts/schema_supabase.sql`, `routers/admin.py` (modelo da linha, INSERT, upload CSV master, sync), `routers/orcamento.py` (importar CSV local/consultas), `services/sync_service.py` e `services/realtime_sync.py` (nuvem → local), `static/orcamento.html` (tabela editável e salvar) e `routers/health.py` (backup). **A LV acompanha exatamente esse caminho.**
- Tabelas envolvidas: `tabela_orcamento_master` (admin, nuvem) e `tabela_orcamento` (do usuário).

## Comportamento desejado (detalhe)
1. **Dado:** `lv` ∈ {`LV`, `LM`, `A`}, padrão `A`. Entrada tolerante: maiúsculas/minúsculas, espaços; vazio/ausente = `A`.
2. **Operação do item é "viva"** quando começa com `*` (`*I`, `*R`, `*M`).
3. **Filtro** (novo `_matches_lv(row)`, combinado com `_matches_origem`): `A` sempre passa; `LV` passa só se a operação do item é viva; `LM` passa só se não é viva.
4. Vale em **todos** os passos da cascata e na expansão do componente e no código direto.
5. Item cujo ativo só existe com o tipo errado (ex.: `*I CAA2` e só há linhas LM) → vai para **"não encontrados"** (com dica "existe só para linha morta"/"só para linha viva").
6. **Migração:** `ALTER TABLE … ADD COLUMN lv TEXT DEFAULT 'A'` nas duas tabelas + `UPDATE … SET lv='A' WHERE lv IS NULL OR lv=''`; Supabase: `ADD COLUMN IF NOT EXISTS lv TEXT DEFAULT 'A'` + mesmo UPDATE (no `schema_supabase.sql`, idempotente).
7. **CSV:** cabeçalho opcional `LV`; arquivos antigos (sem a coluna) → `A`; valor inválido → a importação recusa a linha com mensagem (decisão 2). Exportação/backup incluem a coluna.
8. **Tela de edição da base** (`orcamento.html`): coluna LV com lista (LV/LM/A), nova linha nasce `A`.
