# TASK-046-06-10-2026

**`adicionar_ativo` aceita ativo dinâmico (nome = código encontrado na própria linha, com prefixo/sufixo)**

> Pedido do usuário: "CASO TENHA UM TRAFO MONO TR1* ADICIONE COM A MESMA QUANTIDADE NEGATIVA O TEXTO
> TR1* ACRESCIDO COM VP NO FIM DESSE TEXTO" — o nome do ativo adicionado deve ser o CÓDIGO
> especificamente encontrado na linha (ex.: `TR110`, `TR115`, `TR127`...), não um texto fixo
> `"TR1*VP"` (que não é um código válido). Implementada em 2026-10-06, logo após a TASK-045
> (quantidade dinâmica), dentro do mesmo pedido de regras de ajuste em contexto (TASK-044).

## Objetivo

Permitir que `adicionar_ativo` use um **nome de ativo dinâmico** — `<prefixo><código encontrado na
própria linha por um seletor>><sufixo>` — em vez de só um código fixo no JSON. Cada item da linha
que casa com o seletor gera o seu próprio token novo (ex.: `TR110` e `TR115` na mesma linha geram
`TR110VP` e `TR115VP`, cada um com a quantidade daquele item específico).

## Contexto

TASK-045 já tinha resolvido o problema análogo para `qtd` (quantidade dinâmica = soma de outro
ativo da linha). Este pedido é o mesmo problema, mas para o campo `ativo`: o texto adicionado
precisa **copiar o código realmente encontrado**, não um literal fixo — `"TR1*"` é um curinga de
busca, nunca um código de ativo de verdade.

Peças já existentes reaproveitadas, sem nenhuma mudança: `_contexto(tabela, texto, grupos)` (devolve
os itens `{ativo, qtd}` da própria linha) e `_casa(nome, sel, grupos)` (mesmo motor de seletor usado
em `quando`, `remover_ativo.ativo` e, desde a TASK-045, `qtd.soma`).

## Situação atual (antes desta tarefa)

- `adicionar_ativo.ativo` só aceitava uma string fixa (código sem espaços).
- `descrever_acao()` e a UI só sabiam mostrar/editar um código fixo.

## Comportamento desejado

1. `ativo` passa a aceitar, além de string: `{"igual_a": SELETOR, "prefixo"?: texto, "sufixo"?:
   texto}` — para CADA item da própria linha que casa com `SELETOR` (mesma linguagem de seletor de
   sempre), gera um novo token `"<prefixo><código do item><sufixo>"`, com quantidade = quantidade
   DAQUELE item × `qtd` (aqui `qtd` é usado como FATOR por item, não como soma — não aceita
   `{"soma": ...}` combinado com ativo dinâmico).
2. Nenhum item casa com `SELETOR` na linha → não adiciona nada (no-op, não erro) — mesmo padrão da
   TASK-045.
3. Vários itens casam na mesma linha → um token novo para cada um.
4. **Idempotência preservada:** como `igual_a` tipicamente é um curinga amplo (ex.: `"TR1*"") que
   também casaria com o próprio token recém-criado (`"TR110VP"` começa com `"TR1"`), um item cujo
   nome já carrega o `prefixo`/`sufixo` configurado é excluído dos candidatos — sem isso, reaplicar
   a ação indefinidamente geraria `"TR110VPVP"`, `"TR110VPVPVP"`...
5. `descrever_acao()` descreve o caso dinâmico em português: "para cada TR1* encontrado na linha,
   adicionar código encontrado + 'VP', com a mesma quantidade negativa à linha...".
6. UI (`painel_ajustes.js`): seletor "ativo": `fixo` (como sempre) ou `igual ao ativo encontrado` —
   nesse segundo modo, aparecem os campos "igual a" (seletor), "prefixo" e "sufixo" (texto livre,
   ambos opcionais), e o campo `qtd` vira só "fator" (sem a opção de quantidade dinâmica por soma,
   que não faz sentido combinada com ativo dinâmico).
7. Exemplo exato do pedido do usuário: `{"acao": "adicionar_ativo", "tabela": "outros", "ativo":
   {"igual_a": "TR1*", "sufixo": "VP"}, "qtd": -1, "quando": {"tem": "TR1*"}}`.

## Restrições

- [x] Nenhum dos contratos listados em `RULES.md` (Regra 5) muda — só o JSON de CADASTRO da ação
  ganhou uma forma alternativa para `ativo`.
- `adicionar_ativo` continua restrito a Outros (`SO_OUTROS`).
- Nenhuma mudança em `services/regras_dominio.py`.
- Com ativo dinâmico, `qtd` não aceita `{"soma": ...}` (a soma dinâmica da TASK-045 não faz sentido
  aqui: cada item encontrado já gera seu próprio token com a própria quantidade).

## Critérios de aceite

- [x] `{"igual_a": "TR1*", "sufixo": "VP"}` com `qtd: -1` numa linha com `1-TR110` adiciona
  `*1-TR110VP`.
- [x] Sem `qtd` (padrão 1, fator positivo), a quantidade fica igual à do item encontrado.
- [x] `prefixo` e `sufixo` juntos funcionam (`"X"` + código + `"Y"`).
- [x] Nenhum item casa com `igual_a` → não altera a linha, `operacoes` vazio.
- [x] Vários itens casam na mesma linha → um token novo por item.
- [x] `se_ja_existe: "somar"` funciona com ativo dinâmico, inclusive reaplicando sobre um token já
  gerado por uma rodada anterior (sem duplicar o sufixo/prefixo — guard de idempotência).
- [x] Validação rejeita `ativo` dict sem `igual_a`, com campo desconhecido, `prefixo`/`sufixo` com
  espaço, seletor/`@GRUPO` inexistente, e `qtd` que não é um fator numérico diferente de zero
  (rejeita `{"soma": ...}` combinado com ativo dinâmico).
- [x] `descrever_acao()` gera frase em português correta para ativo dinâmico.
- [x] UI: alternar "ativo" para dinâmico mostra os campos certos e produz o JSON esperado
  (confirmado via Playwright).
- [x] Documentação `.ai` atualizada conforme `RULES.md` Regra 9.
- [x] `STATE.md` atualizado conforme `RULES.md` Regra 10.

## Riscos

- **Idempotência com curinga amplo + prefixo/sufixo:** `igual_a: "TR1*"` casa com o próprio token
  recém-gerado (`"TR110VP"` começa com `"TR1"`). Mitigado excluindo dos candidatos qualquer item
  cujo nome já termina com o `sufixo` configurado ou já começa com o `prefixo` configurado —
  verificado com teste que reaplica a ação sobre uma linha que já contém o token gerado.
- Um teste inicial usou `prefixo`/`sufixo` hifenados (`"X-"`/`"-Y"`) e expôs o MESMO guard de
  contrato pré-existente (`C1-OUT-NUM`, item 31 do STATE.md) já encontrado na TASK-045 — ajustado
  para caracteres sem hífen (fora do escopo desta tarefa, já documentado).
