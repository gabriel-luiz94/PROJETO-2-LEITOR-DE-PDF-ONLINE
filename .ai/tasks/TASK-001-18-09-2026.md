# TASK-001-18-09-2026

## Objetivo

Restabelecer conexão com o banco de dados de usuários.

## Contexto

O banco de dados de usuário está na nuvem, no Supabase (tabela `usuarios_nuvem`,
ver `ARCHITECTURE.md §4.2` e `ADR-001`).

## Situação atual

Não é possível entrar mesmo com credenciais válidas. Também não se consegue cadastrar novos
usuários.

## Comportamento desejado

- Seja possível fazer login com usuário e senha cadastrados no banco de dados do Supabase.
- Seja possível que usuários admin consigam cadastrar novos usuários.

## Restrições

Nenhuma lógica relacionada à tabela de orçamento base — essa está funcionando e não deve ser
alterada.

## Critérios de aceite

O usuário e senha cadastrados no Supabase são aceitos no login e o acesso ocorre normalmente.

## Exemplos

### Entrada

Usuário e senha do login.

### Resultado esperado

Login bem-sucedido, com acesso ao sistema.

## Arquivos potencialmente afetados

- `scripts/schema_supabase.sql` — schema versionado da tabela `usuarios_nuvem` diverge do banco real do usuário
- (fora do repo) tabela `usuarios_nuvem` no projeto Supabase real do usuário — precisa de `ALTER TABLE` para ganhar a coluna `role`
- `services/supabase_client.py` / `routers/health.py` — candidato a receber uma checagem de conectividade, para diagnosticar este tipo de problema sem depender de leitura de código

## Diagnóstico (2026-09-18)

Perguntas feitas ao usuário e respostas, usadas para isolar a causa (ver RULES.md Regra 2 —
não presumir, perguntar):

| Pergunta | Resposta |
|---|---|
| Mensagem exata do erro de login | `"Credenciais inválidas ou usuário não encontrado"` |
| `SUPABASE_URL`/`SUPABASE_KEY` configuradas no ambiente real | Não confirmado — usuário não tem certeza |
| Colunas reais de `usuarios_nuvem` no Supabase | Tem `is_admin`, **não tem `role`** |
| RLS (Row Level Security) na tabela `usuarios_nuvem` | **Desabilitado** (descarta essa hipótese) |

### Causa confirmada (cadastro de usuários)

A tabela real do usuário no Supabase **não tem a coluna `role`**, mas o código grava `role` nela:

- `routers/admin.py:134-139` (`add_user`) — `INSERT` com `role` → PostgREST rejeita coluna
  inexistente → exceção capturada em `admin.py:140-141`, que devolve ao admin a mensagem
  **enganosa** "Erro ao inserir na nuvem: o e-mail já pode existir." (o e-mail pode nem existir —
  o insert falha sempre, por causa da coluna, não de duplicidade)
- `routers/admin.py:220-226` (`update_role`) — mesmo problema, mas o erro é **engolido
  silenciosamente** (`except Exception: pass`), então a troca de role parece funcionar mas não
  persiste na nuvem

Isso confirma e localiza exatamente o que já estava registrado em `STATE.md`, problema 6.

### Causa do login — ainda não fechada por código

A mensagem `"Credenciais inválidas ou usuário não encontrado"` só é emitida
(`routers/auth.py:135`) quando **nem o Supabase nem o SQLite local** retornam uma linha para o
e-mail. Com RLS descartado, as hipóteses que restam — e que só podem ser verificadas contra o
ambiente real do usuário, não pelo código estático — são:

1. `SUPABASE_URL`/`SUPABASE_KEY` não estão de fato definidas no ambiente onde o app roda
   (Fly.io secrets ou `.env` do desktop) → `get_supabase()` retorna `None` → login cai direto
   para o SQLite local, que não tem o usuário criado na nuvem
2. O e-mail digitado no login não bate exatamente (maiúsculas/minúsculas, espaço) com o e-mail
   salvo na tabela — a comparação (`eq("email", ...)`) é sensível a isso
3. O usuário foi criado em outro lugar do Supabase (ex.: `auth.users`, o sistema de autenticação
   nativo do Supabase) e não na tabela custom `usuarios_nuvem`, que é a única que este projeto lê

## Implementação (2026-09-18)

Plano aprovado pelo usuário. Implementado:

1. **`scripts/schema_supabase.sql`** — adicionada seção 8 (Migrações) com
   `ALTER TABLE public.usuarios_nuvem ADD COLUMN IF NOT EXISTS role TEXT DEFAULT 'operador';`
   Idempotente, documentada, não altera o `CREATE TABLE` original (Regra 5 — compatibilidade).
2. **`routers/health.py`** — `GET /api/health` (rota pública, já existente) ganhou 3 campos novos:
   `supabase_configured` (env vars presentes), `supabase_reachable` (query de fato respondeu) e
   `usuarios_nuvem_has_rows` (ou `supabase_error` quando falha). Nenhum dado de usuário (e-mail,
   hash) é exposto — só booleans e contagem, respeitando RULES.md Regra 11.

**Validação feita** (RULES.md Regra 7 — o projeto não tem testes automatizados, então a
verificação foi manual e real, não apenas leitura de código):
- Instalado um venv com as dependências leves do `requirements.txt` (as pesadas — `pymupdf`,
  `ezdxf`, `google-genai`, `openai`, `pywebview` — foram substituídas por stubs mínimos só para
  permitir o import de `app.py`, já que não alteram nada relacionado a este diagnóstico)
- Subida real do servidor (`python app.py`, `APP_MODE=server`, `HEADLESS=1`) e chamada real a
  `GET /api/health` em dois cenários:
  - **Sem `SUPABASE_URL`/`SUPABASE_KEY`:** `supabase_configured: false`, `supabase_reachable: false`,

  - **Com credenciais definidas mas inválidas:** `supabase_configured: true`, `supabase_reachable: false`,
    `supabase_error: "403 Forbidden"` — confirma que a rota não quebra e reporta o erro real do Supabase
- `banco_resumo.db` criado pelo teste (gitignored) foi removido depois; nenhum dado do
  repositório foi alterado por esses testes

## Pendente do lado do usuário

O usuário precisa, no painel do Supabase (SQL Editor do projeto real — não posso executar isso
por não ter acesso ao projeto):

```sql
ALTER TABLE public.usuarios_nuvem ADD COLUMN IF NOT EXISTS role TEXT DEFAULT 'operador';
```

Depois, chamar `GET /api/health` no ambiente real (produção/desktop) e observar:
- `supabase_configured: false` → confirma a causa do login: variáveis de ambiente não estão
  definidas onde o app roda de fato (Fly.io secrets, ou `.env` do desktop)
- `supabase_configured: true` mas `supabase_reachable: false` → problema de rede/credencial errada
- `supabase_reachable: true` → conexão OK; se o login ainda falhar, a causa é (2) e-mail
  digitado não bate exatamente com o cadastrado, ou (3) usuário foi criado em outro lugar do
  Supabase que não a tabela `usuarios_nuvem`
